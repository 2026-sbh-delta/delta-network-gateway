03

팀 사이의 역할과 연결

추천
담당준비하는 것완료 기준
플랫폼서비스 등록, 사용자 권한, 배포 요청·상태·이력재시작 후에도 작업 상태를 확인하고 안전하게 이어감
인프라팀Terraform, 기본 VM 이미지, 관리 접속, 필요한 통신·권한VM 접속·이미지 다운로드·Docker 실행이 가능
빌드·검사코드 빌드, 이미지 저장, ECS 샌드박스 검사어떤 커밋·이미지를 검사했는지 결과와 함께 기록
배포 WorkerAnsible로 이미지 실행·교체, 헬스 체크·복구정상 확인 후 요청 전환, 실패 시 기존 버전 유지
모니터링 담당OTel 설정, 수집 경로, 서비스 식별자·보관 정책플랫폼에서 해당 서비스의 실제 데이터를 조회

Worker는 시간이 걸리는 배포 작업을 수행하는 실행기입니다. Ansible은 원격 서버에 접속해 정해진 작업을 실행하는 도구입니다.

Terraform은 정해진 입력을 받고, 접속 정보를 반환합니다

방향전달할 정보원칙
플랫폼 → Terraform서비스 ID, 환경, CSP·리전, VM 크기 등급, 네트워크, 앱 포트, 기본 이미지 버전인프라팀이 검증한 선택지만 허용
Terraform → 플랫폼VM ID, 계정·프로젝트, 리전·존, 사설 IP, CPU 아키텍처, 접속 방식, 이미지 저장소 주소전용 JSON 출력. 비밀번호·개인키 제외

앱 이미지·환경변수는 배포 Worker에 전달합니다. 앱 코드만 바뀌면 기존 VM의 이미지를 교체합니다. Terraform 상태는 환경·서비스 경계에 맞춰 분리하고 동시 변경을 잠금으로 제어합니다.

관리 접속과 이미지 다운로드는 서로 다른 경로입니다

AWS

사설 VM + EIC

Worker → EIC → SSHEIC: EC2 Instance Connect Endpoint

이미지는 ECR에서 다운로드합니다. ECR·S3에 필요한 VPC Endpoint와 권한을 준비합니다.

GCP

사설 VM + IAP

Worker → IAP 터널 → SSHOS Login으로 로그인 권한 관리

이미지는 Artifact Registry에서 다운로드합니다. Private Google Access, DNS·경로·권한을 준비합니다.

ON-PREMISE

연결된 서버·로컬 PC

Worker → 사설망/VPN → SSH서버에 도달할 관리 경로 필요

지정한 이미지 저장소에 HTTPS·읽기 권한으로 접근합니다. 실행 OS·CPU도 맞춰야 합니다.

AWS·GCP 저장소에는 검증된 이미지를 복사하고 digest(이미지 내용 식별값)를 확인합니다. Worker의 관리 통신은 고객의 실제 서비스 요청 경로와 별개입니다. Endpoint 비용은 인프라 예산에 포함합니다.

기본 VM은 인프라팀이 준비

OS·Docker·관리 접속·수집 도구를 설치한 VM 이미지를 버전으로 관리합니다. 부팅 시에는 환경별 설정을 적용합니다.

재부팅: Docker 자동 시작 → 컨테이너 unless-stopped → 앱 상태 재확인

배포 작업의 권한은 분리

플랫폼 자체 CI와 고객 앱 배포를 구분합니다. 고객 코드를 실행하는 빌드 작업에 Terraform 관리 권한을 주지 않습니다.

공개 저장소여도 클라우드 접근·CI 실행 인증은 필요합니다. 비밀값은 이미지에 넣지 않고 실행 시 연결합니다.

04

관측과 DB 이전

기존 모니터링에 연결

추천

AWS·GCP의 모니터링을 활용하고, 앱 내부 동작은 OpenTelemetry(OTel)로 공통 계측합니다.

앱 → OTel 수집 경로 → 저장소 → 플랫폼 조회
  • CSP 모니터링: VM·LB·DB 지표, 방화벽·감사 로그
  • OTel: 앱 요청 시간·오류·API와 DB 호출 추적
  • 플랫폼: 배포·이전 진행 상태, 승인·실행 이력

OTel은 저장소나 화면이 아닙니다. Loki·Tempo·Prometheus를 모두 새로 운영할 필요는 없습니다. 로그 전송에는 별도 수집 설정이 필요하며, OTel 사용만으로 여러 클라우드 화면이 자동 통합되지는 않습니다.

서비스·환경 ID를 공통으로 사용작업은 run_id, 요청 추적은 trace_id로 연결합니다. 조회 권한은 프로젝트별로 제한합니다.

AWS → GCP / 온프레미스

이전 방향 합의

한 번에 목적지 하나로 이전합니다. PostgreSQL 간 이전을 우선 가정하며, 엔진·버전·관리형 여부는 확인이 필요합니다.

  1. 01접속·호환성 검사, 백업·복원 확인
  2. 02초기 복사 + 이후 변경 내용 복제
  3. 03데이터 검증 → 전환 승인
  4. 04기존 DB 쓰기 중지 → 마지막 변경 반영 확인
  5. 05앱의 DB 연결 변경 → 실제 읽기·쓰기 확인

복제는 기존 DB 기능·이전 도구를 활용합니다. PostgreSQL 논리 복제의 스키마·시퀀스 처리는 별도로 필요합니다. 엔진 변환은 범위에 포함하지 않습니다.

앱 복구와 DB 복구는 별개입니다.
새 DB에 쓰기가 시작되면 이전 DB로 주소만 되돌릴 수 없습니다. 플랫폼의 작업 상태 DB도 이전 대상인 고객 DB와 분리합니다.
05

구현 전에 결정할 것

확인 필요
  • CPU 아키텍처 통일현재 설정은 AWS·ECS ARM64 / GCP x86_64. 첫 지원은 linux/amd64 통일을 추천하며, 기존 설정 변경 합의가 필요합니다.
  • 서비스 주소와 요청 전환사용자 접속 도메인·LB, 새 버전으로 요청을 바꾸는 방법과 실패 기준을 정합니다. VM 관리 접속과는 별도입니다.
  • DB의 실제 구성엔진·버전, AWS RDS인지 VM 설치형인지, 목적지 DB 유형과 허용 가능한 쓰기 중단 시간을 확인합니다.
  • 관측 데이터의 조회·보관팀이 이미 사용하는 수집 도구와 저장소를 확인합니다. 플랫폼 API 연동, 조회 권한, 보관 기간을 정합니다.
