DELTA PLATFORM · 이전 설계

서비스 위치를 바꾸면서
도메인과 로그인 상태를 유지합니다

프론트엔드, 백엔드, PostgreSQL이 함께 움직이는 서비스를 기준으로 설명합니다. 아래 절차는 목표 설계이며, 실제 클라우드 이전이 이미 끝났다는 뜻은 아닙니다.

이전 흐름

서비스와 환경은 플랫폼에서 안정된 식별자로 연결합니다. AWS에서 시작하든 다른 지원 환경에서 시작하든 승인과 데이터 검증 단계는 같습니다.

1 · 초기 복사원본 PostgreSQL의 기준 데이터를 대상에 복사합니다.
2 · 변경 동기화CDC로 복사 이후의 변경을 따라잡습니다.
3 · 대상 검증격리된 검증 환경에서 앱, 데이터, 세션 동작을 확인합니다.
4 · 승인과 전환승인 후 쓰기를 잠시 멈추고 최종 동기화, 단일 작성자 전환을 합니다.

프론트엔드와 백엔드는 새 실행 환경에서 같은 서비스 도메인을 사용합니다. PostgreSQL의 사용자·세션 데이터도 보존해 기존 로그인 상태를 이어가도록 합니다. 이전 중에는 구버전 앱과 신버전 앱 모두 같은 쓰기 DB를 바라보게 하며, 트래픽 분할 자체가 두 DB의 동시 쓰기를 만들지 않도록 합니다.

대상 환경별 확인

Google Cloud

대상 네트워크, 앱 연결, PostgreSQL 복제·지연, 읽기와 쓰기, 도메인 경로를 해당 GCP 환경에서 확인합니다.

온프레미스

사설 연결과 방화벽 경로, 앱 연결, PostgreSQL 복제·지연, 읽기와 쓰기, 도메인 경로를 해당 온프레미스 환경에서 확인합니다.

두 대상은 각각 별도로 검증합니다. 어느 쪽도 다른 쪽의 검증 결과만으로 완료 처리하지 않습니다. 서비스 데이터는 하나의 공유 데이터 계층을 사용하고, 전환 시점의 쓰기 주체는 하나로 유지합니다.

전환 절차

  1. 대상 앱을 샌드박스에서 실행하고 테스트 DB로 연결해 기능을 검증합니다. 이 단계는 실제 고객 DB에 쓰지 않습니다.
  2. 데이터 일치, CDC 지연, 앱 준비 상태, 세션 확인 결과와 승인 대상 입력을 검토합니다.
  3. 승인된 짧은 쓰기 중지 구간에 신규 쓰기와 배치를 멈추고, CDC가 따라잡은 뒤 최종 동기화를 확인합니다.
  4. 쓰기 연결을 대상 PostgreSQL 하나로 전환하고 새 앱 경로를 엽니다. 읽기·쓰기와 기존 로그인 세션을 확인한 뒤 쓰기를 재개합니다.
복구 경계: 대상 DB에서 새 쓰기가 시작된 뒤에는 DNS를 원래 위치로 돌리는 것만으로 안전하게 롤백할 수 없습니다. 원본과 대상 데이터가 달라질 수 있으므로, 사전 계획된 역방향 동기화나 별도 복구 절차 없이 이전 DB로 되돌리지 않습니다.
이 페이지는 이전 절차의 의도된 설계를 설명합니다. 환경별 연결, 운영 승인, 실제 복제 및 전환 결과는 별도 검증 기록으로 확인합니다.
