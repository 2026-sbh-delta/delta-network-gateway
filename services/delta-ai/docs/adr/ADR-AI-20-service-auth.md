# ADR-AI-20: 판단 API를 어떻게 인증할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 호출자를 어떻게 확인할 것인가?
- 현재 문제와 배경: 이 API는 코드와 환경 정보를 받고, 규칙 승인으로 이후 검사를 바꿀 수 있다. 호출 주체와 네트워크 위치는 아직 미정이다.
- 범위: 서비스 간 인증을 다룬다. 사용자 로그인은 다루지 않는다.

## Decision Drivers

1. 인증 없이 호출되지 않는다.
2. 호출자가 어떤 언어든 바로 붙는다.
3. 클라우드를 옮겨도 동작한다.

## Considered Options

### Option A: 고정 Bearer 토큰 (현재 구현)

- 설명: `DELTA_API_TOKEN`을 상수 시간으로 비교한다. 토큰이 없으면 서비스가 시작되지 않는다. `/healthz`만 예외다.
- 장점: 구현과 연동이 가장 쉽고 클라우드에 묶이지 않는다.
- 단점 및 위험: 토큰 하나를 공유해 호출자를 구분하지 못한다. 유출되면 교체 전까지 위험하다. 규칙 승인도 같은 토큰이어서 호출자가 승인까지 할 수 있고 `approver`는 입력값을 그대로 기록한다.

### Option B: 호출자별 토큰과 범위

- 설명: 판단 호출과 규칙 승인 토큰을 나눈다.
- 장점: 에이전트가 자기 규칙을 승인하지 못하게 할 수 있다. 추가 인프라가 없다.
- 단점 및 위험: 토큰 설정과 범위 검사 코드가 조금 늘어난다.

### Option C: mTLS

- 설명: 서비스 간 인증서를 쓴다.
- 장점: 강한 상호 인증이다.
- 단점 및 위험: 인증서 발급과 게이트웨이 설정이 필요하다.

### Option D: 클라우드 IAM·OIDC

- 설명: SigV4나 워크로드 ID 토큰을 검증한다.
- 장점: 장기 비밀이 사라진다.
- 단점 및 위험: 호출 환경에 따라 검증 경로가 달라진다. 멀티 클라우드 설정 시간이 크다.

## Decision

- 선택: Option A로 연동을 시작하고, ADR-AI-05의 Option C를 택하면 Option B를 권고한다.
- 결정 이유: 지금은 연동 속도가 중요하다. 다만 에이전트가 호출자이면 수정안을 낸 쪽이 규칙까지 승인할 수 있어 Option B가 필요하다.
- 감수한 트레이드오프: A에서는 호출자 감사가 약하고 토큰 공유에 의존한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 인터넷에 직접 노출하면 게이트웨이의 TLS와 접근 제한을 전제로 다시 본다.

## Follow-up

- **변경 권고:** 본문 크기 제한은 `Content-Length` 헤더만 본다. 헤더 없이 보낸 11MB 요청이 413 없이 검증 단계까지 도달하는 것을 확인했으므로, 외부 노출 전에 실제 읽은 크기로 제한하거나 게이트웨이에서 제한한다.
- TLS는 서비스 앞 게이트웨이에서 처리하며, 서비스는 내부망에만 둔다.
