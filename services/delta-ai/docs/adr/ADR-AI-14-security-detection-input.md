# ADR-AI-14: 코드 취약점 탐지를 무엇으로 할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 코드 취약점을 무엇으로 찾고 판단 서비스에 어떻게 넘길 것인가?
- 현재 문제와 배경: 10/31 회의에서 정적 코드 검사로 먼저 탐지한 뒤 AI가 수정하기로 했다. 현재 서비스는 SARIF를 입력받고, 픽스처는 Semgrep 실제 실행 결과다.
- 범위: SAST 입력을 다룬다. SCA는 시간상 제외한다. DAST 결과는 `attack_results`로 따로 받는다.

## Decision Drivers

1. 탐지 근거가 결정적이다.
2. 스캐너를 바꿔도 서비스가 바뀌지 않는다.
3. 시연 시간 안에 끝난다.

## Considered Options

### Option A: 호출자가 스캐너를 돌리고 SARIF 전달 (현재 구현)

- 설명: CI나 에이전트가 Semgrep을 실행하고 SARIF와 원본 파일을 보낸다.
- 장점: SARIF를 내는 도구면 교체할 수 있다. 서비스에 저장소 접근과 스캔 실행이 필요 없다.
- 단점 및 위험: 호출자가 스캔 단계를 만들어야 한다. 서비스는 SARIF가 실제 실행 결과인지 검증하지 못한다.

### Option B: 서비스가 Semgrep 직접 실행

- 설명: 코드만 받아 서비스 안에서 스캔한다.
- 장점: 호출이 단순하고 패치 후 재검사를 서비스 안에서 할 수 있다.
- 단점 및 위험: 이미지가 커지고 스캔 시간이 요청 지연에 더해진다.

### Option C: LLM만으로 탐지

- 설명: 코드를 읽고 LLM이 취약점을 찾는다.
- 장점: 스캐너 없이 문맥형 문제까지 볼 수 있다.
- 단점 및 위험: 결과가 재현되지 않고 입력 글에 조종될 수 있다. 회의 결정과도 다르다.

### Option D: CodeQL·상용 스캐너

- 설명: 더 깊은 데이터 흐름 분석을 쓴다.
- 장점: 복잡한 흐름의 탐지력이 높을 수 있다.
- 단점 및 위험: 빌드와 설정에 시간이 들고 라이선스 확인이 필요하다. SARIF를 내면 Option A 구조에 그대로 붙는다.

### Option E: AWS Security Agent 활용

- 설명: OPTION C 문서의 미결 질문처럼 관리형 보안 에이전트를 쓴다.
- 장점: 직접 만드는 범위가 줄 수 있다.
- 단점 및 위험: AWS에 묶인다. 기능, 비용, 출력 형식을 확인하지 않았다.

## Decision

- 선택: Option A, 스캐너는 Semgrep
- 결정 이유: 회의 결정과 맞고 실제 실행 결과로 이미 확인했다. 판단 계약이 스캐너에 묶이지 않는다.
- 감수한 트레이드오프: 서비스 혼자서는 탐지할 수 없고, 패치 후 재검사도 호출자가 다시 스캔해야 한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 호출자가 스캔을 맡기 어려우면 Option B로 옮긴다.

## Follow-up

- 스캔 실행 위치를 CI와 에이전트 중에서 정한다.
- Semgrep 관리 규칙은 Semgrep Rules License v1.0 적용 대상이다. 판매 제품이 아닌 해커톤 시연에는 문제가 없어 보이나, 제품화하면 다시 확인하거나 Opengrep과 자체 규칙을 검토한다.
- Prowler 연동(OPTION C)은 출력 형식을 확인한 뒤 별도로 정한다.
