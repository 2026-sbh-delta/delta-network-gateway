# ADR-AI-21: AI 판단 품질을 어떻게 검증할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 프롬프트, 규칙, 모델을 바꿀 때 판단이 나빠지지 않았음을 어떻게 확인할 것인가?
- 현재 문제와 배경: 이번 MVP 평가에서 폐기된 키로 돌렸는데 LLM 호출 0건으로 통과한 일이 있었다. 패치도 형식 검사만으로는 적용 실패를 놓쳤다.
- 범위: 판단 서비스의 품질 검증을 다룬다.

## Decision Drivers

1. 빠른 시험과 실제 LLM 평가를 구분한다.
2. 실제 LLM을 부르지 않은 결과를 통과로 세지 않는다.
3. 추가 플랫폼 없이 돌린다.

## Considered Options

### Option A: pytest, 평가 YAML, 3가지 실행 모드 (현재 구현)

- 설명: 테스트 98개는 가짜 LLM으로 돈다. `eval/cases.yaml` 13건을 `none`, `fake`, `claude`로 돌린다. `claude`는 호출 0건이면 실패로 끝난다. 패치는 별도로 실제 `git apply`와 Semgrep 재검사까지 확인했다.
- 장점: 외부 서비스가 없고 비용을 조절할 수 있다. 판정, 규칙, 적용 가능성을 함께 본다.
- 단점 및 위험: 평가 항목이 손으로 쓴 13건이고 코드 보안은 2건이다. `feedback_ingest`는 평가셋에 없고 단위 테스트로만 본다. 설명 문장의 품질은 채점하지 않는다.

### Option B: 평가 플랫폼

- 설명: promptfoo, LangSmith 등을 쓴다.
- 장점: 기록과 비교 화면을 얻는다.
- 단점 및 위험: 도구 학습과 데이터 전송 검토가 필요하다. 지금 평가량에서는 이득이 작다.

### Option C: 단위 테스트만

- 설명: 가짜 LLM만 돌린다.
- 장점: 무료이고 빠르다.
- 단점 및 위험: 실제 모델의 패치 실패와 형식 오류를 놓친다. 이번 줄 번호 오류도 실제 평가에서 찾았다.

### Option D: 실제 앱 대상 종단 시험

- 설명: 샌드박스에서 공격, 패치, 재공격까지 돌린다.
- 장점: 시연과 가장 가깝고 가장 강한 증거다.
- 단점 및 위험: 다른 담당의 구성요소가 있어야 하고 실행이 오래 걸린다.

## Decision

- 선택: 지금은 Option A. 통합이 되면 Option D를 시연 리허설로 추가한다.
- 결정 이유: 현재 입력만으로 회귀를 잡을 수 있고 빠르게 돌릴 수 있다.
- 감수한 트레이드오프: 13건 통과가 실제 앱에서의 품질을 뜻하지 않는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 데모 앱이 정해지면 평가 항목을 그 코드로 바꾼다.

## Follow-up

- 데모 앱과 팀 실제 결과 형식으로 평가셋을 다시 만든다.
- `feedback_ingest` 평가 항목을 추가한다.
