# ADR-AI-19: 규칙 후보를 어디에 저장할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 규칙 후보와 승인 상태를 어디에 둘 것인가?
- 현재 문제와 배경: 후보는 재시작 후에도 남아야 다음 검사에 쓰인다. 공유 인프라와 DB는 아직 정해지지 않았다.
- 범위: 규칙 후보만 다룬다. 판단 이력 저장은 현재 없다.

## Decision Drivers

1. 인프라 없이 오늘 동작한다.
2. 시연 중 재시작해도 후보를 잃지 않는다.
3. 나중에 교체 비용이 작다.

## Considered Options

### Option A: JSON 파일 (현재 구현)

- 설명: `RuleStore`가 임시 파일에 쓰고 원자적으로 교체한다.
- 장점: 의존성이 없고 내용을 눈으로 확인할 수 있다.
- 단점 및 위험: 프로세스 1개가 전제다. 여러 인스턴스나 워커에서는 갱신이 유실될 수 있다. 컨테이너에 볼륨이 없으면 재시작할 때 사라진다.

### Option B: PostgreSQL

- 설명: 데모 앱이나 플랫폼의 DB에 테이블을 둔다.
- 장점: 동시 갱신과 이력에 강하다.
- 단점 및 위험: 스키마와 접속 정보 관리가 필요하다. 플랫폼 DB가 아직 정해지지 않았다.

### Option C: Git 저장소의 규칙 파일

- 설명: 승인된 규칙을 저장소 파일로 관리한다.
- 장점: 이력과 승인이 코드 리뷰와 합쳐진다.
- 단점 및 위험: 공유 레포가 먼저 있어야 하고 쓰기 권한이 필요하다.

### Option D: 관리형 키-값 저장소

- 설명: DynamoDB나 Firestore를 쓴다.
- 장점: 여러 인스턴스를 지원한다.
- 단점 및 위험: 특정 클라우드에 묶여 이전 시나리오와 충돌한다.

## Decision

- 선택: Option A 유지. 인스턴스를 늘리거나 플랫폼 DB가 정해지면 Option B로 바꾼다.
- 결정 이유: 지금 필요한 규모는 후보 몇 개와 인스턴스 하나다. 접근이 `RuleStore` 한 클래스로 모여 있다.
- 감수한 트레이드오프: 서비스를 1개로만 띄워야 한다. 감사 이력은 마지막 상태와 승인자만 남는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: HA 구성이나 동시 승인이 시연 범위에 들어오면 바꾼다.

## Follow-up
