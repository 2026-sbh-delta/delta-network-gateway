# ADR-AI-30: Jenkins 에 Argo CD 를 더할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 팀 결정이 필요하다. Argo CD 는 본선 구조에서 시험하지 않았다.

## Context

- 결정할 질문: Jenkins 가 빌드하고 Argo CD 가 배포 저장소를 동기화해 각 k8s 클러스터로 내보내는 구조를 쓸 것인가?
- 현재 문제와 배경:
  - 11/01 회의록에 CI/CD 도구가 미정으로 남았고 조사는 김연재 담당이다. 호원 님은 클러스터 비용 때문에 Jenkins 우선을 제안했다.
  - main 의 Terraform 에는 k8s 가 없고 AWS·GCP VM 만 있다. k8s 는 온프레미스 k3s 뿐이다.
  - 호원 님이 11/02 에 배포 서브넷·NAT GW·medium 상향을 하겠다고 답했다. 코드에는 아직 없지만 네트워크와 크기는 결정적 제약이 아니다.
  - 11/02 회의에서 호원 님은 고객 앱을 EC2 에 올리는 쪽이 플랫폼 차이를 보여 주기에 적합하다고 했고, 준우 님의 스테이징 설계는 ECS Fargate 다. 고객 앱 인프라는 확정 전이다.
- 범위: 배포 도구만 다룬다. 트래픽 앞단은 [ADR-AI-37](ADR-AI-37-aws-front-door.md)에서 다룬다.

## Decision Drivers

1. 카나리 단계마다 AI 판단을 받고 즉시 롤백할 수 있다.
2. 환경마다 같은 방식으로 배포해 클라우드에 묶이지 않는다.
3. 본선까지 구현하고 안정화할 수 있다.
4. 비용과 실패 지점을 늘리지 않는다.

## Considered Options

### Option A: Jenkins 단독, 배포 단계만 교체 가능하게 유지

- 설명: Jenkins 가 빌드·배포·전환을 모두 맡는다. 배포 단계는 스크립트로 분리해 둔다.
- 장점: 검증한 구조를 쓰고 VM 에도 배포할 수 있다.
- 단점 및 위험: 드리프트 감지와 Git 기반 변경 이력이 없다.

### Option B: Jenkins + Argo CD

- 설명: Jenkins 가 이미지를 올리고 배포 저장소를 고치면 Argo CD 가 동기화한다.
- 장점: 같은 Git 선언으로 여러 환경에 배포한다는 이야기가 테마에 맞고, 드리프트 감지와 변경 이력이 생긴다. 클러스터 안에서 Git 을 당겨 오므로 외부에서 6443 을 열지 않아도 된다.
- 단점 및 위험: AWS·GCP 에 클러스터가 새로 필요하다. 단계별 판단과 클라우드 간 전환은 대신하지 못해 Jenkins 에 남고, Jenkins 가 동기화를 기다리는 지점이 늘어난다. 웹훅이 없으면 기본 폴링이 2~3분이라 시연에서는 수동 동기화가 필요하다.

### Option C: Argo CD + Argo Rollouts 로 전환

- 설명: 클러스터 안의 카나리까지 Argo 로 옮긴다.
- 장점: 클러스터 안 카나리를 표준 방식으로 처리한다.
- 단점 및 위험: 판단 게이트를 다시 만들어야 하고 클라우드 간 전환은 여전히 범위 밖이다. 남은 기간에 비해 변경이 크다.

## Decision

- 선택: Option A 권고.
- 결정 이유: 시연의 핵심인 전환·판단·롤백이 Jenkins 에 남으므로 Argo 가 대신하는 부분이 적고, AWS·GCP 에 k8s 가 없다.
- 감수한 트레이드오프: GitOps 이야기와 드리프트 감지를 포기한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 고객 앱을 k8s 로 운영하기로 정해질 때. 이때는 배포 단계 하나만 Argo CD 동기화로 바꾼다.

## Follow-up

- 고객 앱 인프라를 팀에서 확정한다.
- Jenkins 사용과 AWS 구성도의 CodeBuild·CodeDeploy 중 무엇을 쓸지 팀에서 정한다(ADR-AI-25).
