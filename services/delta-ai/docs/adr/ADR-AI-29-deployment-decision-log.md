# ADR-AI-29: 본선 배포 파이프라인과 AI 판단 연결의 결정 경위

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 확정 전까지 승인된 결정이 아니다. 로컬에서만 구현·검증했고 AWS·GCP 에 배포하지 않았다.

대안 비교와 검증 표는 세부 ADR 에 두고 여기에 다시 적지 않는다: 25(게이트), 27(역할·구동), 28(패치 경계), 30(Argo), 31(발표), 35(main 맞춤), 36(사전 확인). 이 문서는 2026-11-01~02 에 어떤 순서로, 무엇을 근거로 정했는지 모은다.

## Context

- 결정할 질문: 본선 배포 파이프라인을 어떤 구조로 만들고, 로그·지표·오류를 AI 판단과 어떻게 연결할 것인가?
- 현재 문제와 배경:
  - 11/01 회의에서 배포 파이프라인 구현과 Jenkins·ArgoCD 조사를 김연재가 맡았다. 도구는 미정으로 남았고, 호원 님이 클러스터 비용 때문에 Jenkins 우선 검토를 제안했다.
  - 공유된 구성도는 CodeCommit·CodeBuild·CodeDeploy 기반이다. 읽기 전용으로 본 계정에는 이 서비스들이 없었고, Workload 관리자 역할의 생성 권한은 시뮬레이션에서 허용됐다.
  - AWS 서버는 공인 IP 없는 `t4g.nano` 2대였고 쿠버네티스와 NAT 는 없었다.
- 범위: 파이프라인과 판단 서비스의 연결을 다룬다. 진입점(게이트웨이) 설계와 데이터 이전은 다루지 않는다.

## Decision Drivers

1. 나쁜 배포는 사람과 LLM 없이도 멈춘다.
2. 판단 서비스 장애가 배포 통과로 이어지지 않는다.
3. 판정은 코드가 정해 재현할 수 있다. LLM 은 설명과 패치 제안만 한다.
4. 특정 클라우드에 묶지 않는다(Beyond Lock-In).
5. 담당 경계를 지키고 본선(11/07)까지 구현할 수 있다.

## 결정 경위

| # | 질문 | 선택 | 상태 |
|---|---|---|---|

| 2 | AI 판단 연결 | 단계별 게이트 호출 | 로컬 검증 (ADR-AI-25) |

### 1. CI/CD 도구

- Option A Jenkins: 도구가 클라우드 밖에 있고 파이프라인 안에 판단·사람 승인을 넣기 쉽다. 서버 운영과 보안 설정을 직접 맡는다.
- Option B Argo CD: 예선에서 쓴 방식이다. AWS·GCP 에 클러스터가 없다. 비교는 ADR-AI-30 에 있다.
- Option C AWS Code 계열: 관리 부담이 작지만 GCP·온프레미스 배포와 맞지 않고 AWS 에 묶인다. 공유 구성도의 안이다.
- Option D GitHub Actions: 10/31 회의에서 검토 대상이었다. 비교 시험은 하지 않았다. 사설망 안 서버로 배포하려면 사설 runner 가 필요하다.
- 선택: Option A 권고. 근거는 위 비교와 로컬 시험이다. 호출부가 스크립트라 다른 CI 로 옮길 수 있다.
- 주의: 사용자 전달로 Jenkins 로 진행했지만 회의록에 확정 기록은 없다. 고객 앱이 쿠버네티스로 정해지면 배포 단계만 Argo 로 바꾼다.

### 2. AI 판단 연결

- 단계마다 요약 근거를 `POST /v1/assessments` 로 보내는 방식을 골랐다.
- 로그 전체를 LLM 에 스트리밍하는 안은 비용과 지연이 크고 판정이 재현되지 않아 뺐다.
- 판단 서비스가 배포를 직접 실행하는 안은 ADR-AI-05 와 충돌해 뺐다.

### 3. 로컬 우선

- 서버·NAT·트래픽 전환 지점이 준비되지 않아 Docker Compose 로 Jenkins, HAProxy 대역, 카나리 슬롯을 만들었다.
- 호원 님께는 당장 작업이 아닌 참고용으로 필요한 항목을 먼저 공유했다(11/02 00:31, 사용자 전송).
- 대가: 사설망, ANF, 실제 서버 메모리, 교차 배포는 확인하지 못한다.

### 4. 롤백과 판단 실패

- 지표 기준(오류율 0.05, p95 500ms, 표본 20건)을 넘으면 파이프라인이 먼저 되돌리고 LLM 은 그 뒤 설명만 한다. 시험대의 p95 기준은 Mac 부하 오탐 때문에 나중에 2000ms 로 올렸다(#78~).
- 표본 부족과 지표 누락은 `needs_human` 이다. 판단 서비스 응답이 없으면 통과가 아니다.
- 대가: 카나리 비율만큼은 사용자가 오류를 받는다(초기 빌드 #4 에서 외부 클라이언트가 500 을 4건 받았다). 시연에서 "오류 0" 이라고 말하지 않는다.

### 5. 실패 피드백 루프

실제 Claude 로 평가하니 멈추고 설명하는 데까지는 동작했지만, 세 곳이 비어 있었다. 작은 것부터 채웠다.

| 빈 곳 | 평가 결과 | 선택 |
|---|---|---|
| 카나리 원인 분석 | 앱 로그가 없어 "원인 불명" (#28, #29) | 롤백 전 로그 50줄 전달. #33 에서 `FAIL_RATE=0.5` 를 지목 |
| 같은 실패 재발 | 같은 문제가 10% 에 다시 노출 (#29) | 코드+런타임 설정 해시로 기록, 재시도는 사람 승인. #34 에서 트래픽 전에 멈춤 |
| 패치 적용 | 평가 스크립트만 적용 | 네트워크 없는 샌드박스에서 테스트·재검사·재판단, 최대 2회, 사람 승인 뒤 반영. #41~43 |

- 자동 배포는 고르지 않았다. 패치는 판단 경로를 바꿀 수 있는 입력이라 사람 승인을 남겼다.
- 해시를 쓴 이유: 시험대에 실제 commit 전달이 없고, 같은 코드라도 런타임 설정이 다르면 다른 릴리스이기 때문이다.

### 6. `code_security` 제거 대응

PR #3 으로 패치 출처가 사라졌고, 코드 보안은 준우 님 담당이므로 되살리지 않았다. 대안과 검증은 ADR-AI-35 에 있다.

### 7. 판단 서비스 사전 확인

6 이후 SAST 가 판단 서비스를 부르지 않아 장애를 카나리 10% 에서야 알게 됐다(#59). 첫 단계 확인을 넣어 트래픽 변경 0회로 중단하게 했다(#63). 대안과 검증은 ADR-AI-36 에 있다.

### 8. DAST 결과 판정

ADR-AI-27 참고. 시연 콘솔로 세 시나리오를 이었다(#68~81). 재검증은 준비된 수정 비교군(`fixed`)을 점검하므로 실제 패치 검증이 아니다.

### 9. 패치 출처와 검토

ADR-AI-28 참고. `/fix` 를 실제로 돌려 쓸 만한 패치를 확인했지만 패치 빌드 재검증 경로가 없다. 준우 님은 판단 문서를 참고해 패치를 만들고, 통과 여부는 실행 증거로 delta-ai 가 판정하는 구조를 권고한다.

### 10. 트래픽 전환 지점

- 처음에는 HAProxy 를 전제로 대역을 만들었다. 11/02 동규 님이 HAProxy 를 기본 구성에서 빼고 관리형 LB 를 쓰는 안을 냈고, 호원 님은 중앙관리 솔루션 설계에서 대안 1(공통 진입점)과 대안 2(고객사별 진입점)를 비교했다. 호원 님은 대안 1 의 명확한 이점이 없으면 대안 2 를 기본으로 하고 HAProxy 는 필요한 구간에만 쓰자고 제안했다. 저녁까지 결론은 없다.
- 결론을 기다리지 않고 진행할 수 있도록 파이프라인에는 비율 변경, 상태 조회, 즉시 원복만 요구한다. 결정되면 `haproxy_ctl.py` 만 바꾼다.

### 11. 서버 네트워크

11/02 호원 님 답변: 배포 서브넷과 NAT GW 구성, Jenkins 대역이 정해지면 SSH 허용, 인스턴스를 medium 으로 상향.

- 처음에 후보로 쓴 `10.40.0.0/16` 은 온프레미스 데모망 `10.40.0.0/24` 와 겹친다. 다른 대역으로 바꿔야 한다.
- 발표에서 Jenkins 화면을 보여 줄지는 팀 논의가 필요하다. 전체 소요 시간은 측정하지 않았으니, 미리 돌린 결과와 카나리 롤백만 라이브로 잡는 안을 권고한다.

## Decision

- 선택: Jenkins 가 구동하고, 관측 도구는 증거를 내고, delta-ai 가 코드로 판정하고, 사람이 위험 변경을 승인하는 구조를 권고한다.
- 결정 이유: 로컬 빌드에서 자동 롤백, 판단 불가 시 중단, 재발 차단, 사람 확인을 실제로 확인했다.
- 감수한 트레이드오프: 규칙에 없는 이상은 게이트가 못 잡는다. Jenkins 서버 운영을 직접 맡는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 고객 앱이 쿠버네티스로 정해지거나, 팀이 AWS 구성도를 택하거나, 본선까지 Jenkins 서버를 올릴 경로가 없을 때.

## 확인하지 못한 것

- 사설망·ANF·실제 서버·AWS→GCP 교차 배포·ARM/x86 빌드.
- 실패 기록이 있는 릴리스가 승격에 성공할 때 기록이 지워지는지(단위 테스트만).
- 샌드박스 테스트 실패 경로(단위 테스트만).
- 시연 콘솔에서 판단 서비스가 꺼진 경우(단위 테스트만), AI 에이전트 DAST 와 온프레미스 재수집 버튼.
- 패치 시험은 취약점 1종이라 표본이 작다.

## 알려진 위험

- **고정 p95 500ms 기준의 오탐:** 부하 큰 Mac 에서 오류 0 인 정상 배포가 p95 793~1075ms 로 되돌려졌다(#45, #50, #52). 코드 원인은 찾지 못했고 호스트 부하로 판단한다. 오탐은 재발 기록까지 남긴다. 실제 서버에 쓰기 전에 카나리와 안정 버전 비교로 바꿔야 한다.
- 시험대의 Jenkins 는 root 와 `docker.sock` 을 쓰므로 서버에 그대로 올리지 않는다.
- 데모 이미지는 `app.py` 만 복사해 패치한 `vulnerable.py` 가 실행되지 않고, 승인한 패치가 소스로 돌아가지 않는다.
- DAST 대상(실습 게시판)과 배포 대상(Jenkins 데모 앱)이 달라 같은 릴리스를 점검한다고 말할 수 없다.
- 작업이 브랜치 넷에 나뉘어 있고 푸시하지 않았다. `feat/jenkins-local` 의 ADR-AI-26(`78f5dd2`)은 28 과 내용이 같으므로 합칠 때 뺀다.

## Follow-up

- Jenkins 확정 여부와 발표 범위를 팀에서 정한다.
- 준우 님과 ADR-AI-27·28 을 합의한다. 구동 주체를 먼저 정한다.
- 동규 님과 전환 지점 계약을, 호원 님과 Jenkins 대역을 정한다.
- 서버용 Jenkins 구성, 카나리·안정 비교, 진행 그래프 이벤트(ADR-AI-24)를 구현한다.
