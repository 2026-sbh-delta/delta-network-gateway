# ADR-AI-17: 피드백에서 나온 규칙을 언제 적용할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 긴 코드 리뷰나 모의해킹 보고서에서 나온 규칙을 어떤 절차로 다음 검사에 반영할 것인가?
- 현재 문제와 배경: 피드백 루프를 보여 주려면 지난 결과가 다음 판단을 바꿔야 한다. 그러나 보고서는 외부 입력이므로 그대로 규칙이 되면 검사를 오염시킬 수 있다.
- 범위: 활성화 절차를 다룬다. 탐지기 형식은 ADR-AI-18에서 다룬다.

## Decision Drivers

1. 오염된 보고서가 검사를 바꾸지 못한다.
2. 다음 검사에서 실제로 잡히는 장면을 시연한다.
3. 누가 왜 승인했는지 남는다.

## Considered Options

### Option A: 후보, 회귀 시험, 사람 승인 (현재 구현)

- 설명: LLM이 탐지기를 제안한다. 취약 코드는 잡고 안전 코드는 잡지 않아야 승인할 수 있다. 사람이 승인해야 다음 `code_security`에 적용되고 승인자를 기록한다.
- 장점: 보고서의 지시문이 바로 적용되지 않는다. 시험을 통과하지 못한 후보는 승인 API가 409로 막는다.
- 단점 및 위험: 사람이 없으면 루프가 멈춘다. 시연에 승인 단계가 필요하다. 회귀 시험이 보고서의 코드 조각 한 쌍으로만 돈다.

### Option B: 시험 통과 시 자동 활성화

- 설명: 회귀 시험을 통과하면 바로 적용한다.
- 장점: 사람 없이 루프가 닫혀 시연이 매끄럽다.
- 단점 및 위험: 시험 조각도 보고서에서 오므로 공격자가 함께 조작할 수 있다.

### Option C: 규칙 없이 근거 문서에만 추가

- 설명: 보고서를 검색 문서로 넣는다.
- 장점: 구현이 쉽고 판정 위험이 없다.
- 단점 및 위험: 다음 검사에서 탐지가 늘지 않는다. 피드백으로 잡았다는 장면을 만들 수 없다.

### Option D: 규칙 저장소 PR로 승인

- 설명: 후보를 Git PR로 올리고 머지를 승인으로 본다.
- 장점: 리뷰와 이력이 기존 개발 흐름에 맞는다.
- 단점 및 위험: 공유 레포와 GitHub 연동이 있어야 한다. 시연 시간이 길어질 수 있다.

## Decision

- 선택: Option A. 공유 레포가 안정되면 승인 방식을 Option D로 바꿀 수 있다.
- 결정 이유: 자동화보다 입력 오염 방지가 우선이다. 승인 API 하나로 시연할 수 있다.
- 감수한 트레이드오프: 완전 자동 루프가 아니다. 대시보드에 승인 화면이 없으면 시연이 API 호출로 보인다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 실제 보고서의 형식이 코드 조각 쌍을 줄 수 없으면 회귀 시험 방식을 바꾼다.

## Follow-up

- 보고서 작성자와 입력 형식을 맞춘다.
- 대시보드 담당과 승인 화면 여부를 정한다.
