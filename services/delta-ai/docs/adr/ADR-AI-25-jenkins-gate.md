# ADR-AI-25: 배포 파이프라인과 AI 판단을 어떻게 연결할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 확정 전까지 승인된 결정이 아니다. 로컬에서만 구현·검증했다.

## Context

- 결정할 질문: 배포 파이프라인의 로그·지표·오류를 판단 서비스와 어떻게 주고받고, 누가 승격과 롤백을 정할 것인가?
- 현재 문제와 배경: 사용자가 CI/CD 를 Jenkins 로 정했다고 전했고 트래픽 전환은 우선 HAProxy 로 한다. 다만 Notion·Slack 에서 Jenkins 확정 기록은 찾지 못했다. 공유된 AWS 구성도는 CodeCommit·CodeBuild·CodeDeploy 를 쓰므로 팀 합의가 필요하다.
- 범위: 파이프라인과 판단 서비스의 연결만 다룬다. 서버 위치와 네트워크 경로는 다루지 않는다.

## Decision Drivers

1. 나쁜 배포는 사람과 LLM 없이도 멈춘다.
2. 판단 서비스 장애가 배포 통과로 이어지지 않는다.
3. 시연에서 단계와 판정을 보여 줄 수 있다.
4. 특정 클라우드에 묶지 않는다(Beyond Lock-In).

## Considered Options

### Option A: 단계별 게이트 호출

- 설명: 파이프라인이 단계마다 요약 근거를 `POST /v1/assessments`(`deployment_gate`)로 보내고 판정에 따라 움직인다.
- 장점: 실행과 판단이 분리된다(ADR-AI-05). 판정을 코드가 정해 재현할 수 있다.
- 단점 및 위험: 호출 경로와 토큰을 준비해야 한다. 단계 수만큼 호출이 늘어난다.

### Option B: 로그 전체를 LLM 에 스트리밍

- 설명: 파이프라인 로그를 계속 보내 LLM 이 이상을 찾아 멈춘다.
- 장점: 규칙에 없는 이상도 볼 수 있다.
- 단점 및 위험: 비용과 지연이 크고, 판정이 재현되지 않으며, 로그에 든 지시문에 영향받는다. 롤백이 LLM 을 기다리게 된다.

### Option C: 판단 서비스가 배포를 직접 실행

- 설명: 판단 서비스에 배포 권한을 준다.
- 장점: 흐름이 한곳에 모인다.
- 단점 및 위험: ADR-AI-05 와 충돌한다. 판단 서비스가 뚫리면 배포 권한까지 넘어간다.

## Decision

- 선택: Option A 권고. 도구는 Jenkins 로 시험했고 호출부는 스크립트(`gate.py`)라 다른 CI 로 옮길 수 있다.
- 결정 이유: 2026-11-02 로컬 시나리오에서 오류 카나리 자동 롤백, 판단 불가 시 중단, 사람 확인 대기를 확인했다. 기록은 [jenkins-local.md](../../../../docs/ai-dlc/jenkins-local.md).
- 감수한 트레이드오프: 규칙에 없는 이상은 게이트가 못 잡는다. 카나리 비율만큼은 사용자가 오류를 받는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 팀이 AWS 구성도의 CodeBuild·CodeDeploy 를 택하거나, Jenkins 서버를 사설망에 둘 경로가 없을 때.

## Follow-up

- Jenkins 와 AWS 구성도 중 무엇을 쓸지 팀에서 정한다.
- 사설망 Jenkins 의 외부 경로, ANF 규칙, 서버 크기를 호원 님과 맞춘다.
- 동규 님의 HAProxy 가 나오면 `haproxy_ctl.py` 를 그 설정에 맞춘다.
- `code_security` 제거(PR #3)로 SAST 탐지는 지금 사람이 본다. 패치 출처(DAST `/fix` 검토)와 진행 그래프용 단계 이벤트(ADR-AI-24)를 정한다.
