# ADR-AI-18: 피드백 탐지기를 어떤 형식으로 표현할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: LLM이 제안하는 새 탐지 규칙의 형식을 무엇으로 할 것인가?
- 현재 문제와 배경: LLM이 만든 규칙을 서버에서 실행하므로 실행 안전성이 중요하다. 현재는 임시 형식으로 만들었고 코드 주석에도 임시라고 적었다.
- 범위: 탐지기 표현과 실행을 다룬다.

## Decision Drivers

1. LLM이 만든 규칙이 서버를 위험하게 하지 않는다.
2. 실제 취약점을 놓치지 않고 안전한 코드를 잡지 않는다.
3. 기존 스캐너 흐름에 들어간다.

## Considered Options

### Option A: 한 줄 안의 문자열 조합 (현재 구현)

- 설명: `detector_contains`의 문자열이 한 줄에 모두 있으면 잡는다. 2~4개를 받고, 최대 5개와 길이를 제한한다.
- 장점: 정규식 ReDoS가 없고 구현이 작다. 설명과 회귀 시험이 쉽다.
- 단점 및 위험: 여러 줄에 걸친 코드를 못 잡고 변수명을 바꾸면 놓친다. 데이터 흐름을 보지 못한다. 시연 수준이다.

### Option B: 정규식

- 설명: LLM이 정규식을 낸다.
- 장점: 표현력이 늘어난다.
- 단점 및 위험: ReDoS 대책이 필요하고 잘못 만든 패턴을 사람이 알아보기 어렵다.

### Option C: Semgrep 규칙 생성

- 설명: LLM이 Semgrep YAML을 만들고, 취약·안전 코드로 Semgrep 시험을 돌린 뒤 승인한다.
- 장점: 문법 인식 탐지로 정확도가 높다. SARIF 흐름(ADR-AI-14)과 합쳐진다. "피드백이 실제 스캐너 규칙이 됐다"는 설명이 강하다.
- 단점 및 위험: Semgrep 실행 환경이 필요하다. LLM이 만든 YAML의 품질 시험이 추가로 필요하고 구현 시간이 든다.

### Option D: AST 쿼리 직접 구현

- 설명: tree-sitter 등으로 자체 규칙을 돈다.
- 장점: 정밀하고 외부 스캐너가 필요 없다.
- 단점 및 위험: 언어별 구현 비용이 커서 기간 안에 맞지 않는다.

## Decision

- 선택: 현재 Option A, 데모 앱이 정해지면 Option C로 전환을 권고한다.
- 결정 이유: A는 지금 안전하게 동작하지만 실제 검출력이 약하다. C는 탐지 흐름을 하나로 합치고 시연 설명도 더 강하다.
- 감수한 트레이드오프: 전환 전까지 피드백 탐지는 단순 코드에서만 믿을 수 있다. 전환하면 서비스나 호출자에 Semgrep 실행이 필요해진다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 시간이 부족하면 A로 시연하고 한계를 발표에서 밝힌다.

## Follow-up

- **변경 권고:** 데모 앱 언어와 스캔 위치(ADR-AI-14)가 정해지면 Option C를 구현한다.
