# ADR-AI-03: 판단 결과를 동기로 돌려줄 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 호출자가 응답을 기다리게 할 것인가, 작업 ID를 받아 나중에 조회하게 할 것인가?
- 현재 문제와 배경: 규칙만 도는 판단은 바로 끝나지만 LLM을 부르면 호출마다 시간이 걸린다. 호출 1건당 지연은 아직 따로 재지 않았다.
- 범위: 호출 방식과 시간 제한을 다룬다.

## Decision Drivers

1. 호출자 구현이 단순하다.
2. 호출이 무한정 매달리지 않는다.
3. 시연 흐름이 끊기지 않는다.

## Considered Options

### Option A: 동기 요청·응답 (현재 구현)

- 설명: 판단이 끝날 때까지 HTTP 연결을 유지한다. LLM 일시 오류는 503으로 돌려준다.
- 장점: 호출자 코드와 서버 상태가 가장 단순하다.
- 단점 및 위험: 게이트웨이나 호출자의 시간 제한에 걸릴 수 있다. 연결이 끊기면 결과도 잃는다.

### Option B: 작업 생성 후 조회

- 설명: 202와 ID를 돌려주고 호출자가 결과를 조회한다.
- 장점: 오래 걸려도 연결이 끊기지 않는다. 진행 상태를 대시보드에 보여 줄 수 있다.
- 단점 및 위험: 작업 저장소와 실행기가 필요하다.

### Option C: 콜백·이벤트

- 설명: 끝나면 호출자의 URL이나 큐로 알린다.
- 장점: 호출자가 조회하지 않아도 된다.
- 단점 및 위험: 양쪽 모두 수신 경로와 인증을 만들어야 한다.

## Decision

- 선택: Option A 유지, 단 LLM 호출 시간 제한을 명시하도록 바꾼다.
- 결정 이유: MVP에서 호출자가 가장 빨리 붙는다. 평가셋 판단도 건별로 끝난다.
- 감수한 트레이드오프: 재시도와 시간 제한을 호출자도 함께 관리해야 한다. 진행률을 보여 줄 수 없다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 실제 호출 지연이 게이트웨이 제한을 넘거나 한 번에 여러 판단을 묶게 되면 Option B로 바꾼다.

## Follow-up

- **변경 권고:** `_llm_from_env()`가 시간 제한 없이 `ClaudeLLM`을 만든다. SDK 기본값은 10분 제한과 재시도 2회이고 시간 초과도 재시도되므로, 최악의 경우 응답까지 약 30분이 걸릴 수 있다. `client_options`로 짧은 제한을 넣는다.
- `meta.duration_ms`로 실제 지연을 재서 호출자 제한값을 정한다.
