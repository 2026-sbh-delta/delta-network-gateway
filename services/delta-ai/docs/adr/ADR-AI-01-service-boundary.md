# ADR-AI-01: AI 판단을 어떤 형태로 제공할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 플랫폼과 에이전트가 AI 판단을 어떤 방식으로 호출하게 할 것인가?
- 현재 문제와 배경: 호출 주체와 시점은 오늘 회의에서 정해진다. 공유 레포도 아직 없어 각자 만든 MVP를 언어와 무관하게 붙일 수 있어야 한다.
- 범위: 호출 방식만 다룬다. API 모양은 ADR-AI-02, 동기·비동기는 ADR-AI-03에서 다룬다.

## Decision Drivers

1. 호출 주체가 바뀌어도 다시 만들지 않는다.
2. 팀원이 오늘 바로 호출해 볼 수 있다.
3. 시연 중 장애 지점을 늘리지 않는다.

## Considered Options

### Option A: 독립 HTTP 서비스 (현재 구현)

- 설명: FastAPI 서비스가 `POST /v1/assessments`를 받는다.
- 장점: 언어와 호출 주체에 묶이지 않는다. curl로 바로 시연하고 확인할 수 있다.
- 단점 및 위험: 프로세스를 띄워 둬야 한다. 네트워크 경로와 인증이 필요하다.

### Option B: 파이썬 라이브러리

- 설명: 호출하는 쪽이 패키지를 가져와 함수로 부른다.
- 장점: 서버와 네트워크가 필요 없다.
- 단점 및 위험: 호출자가 파이썬이어야 한다. API 키와 규칙 저장소가 호출자마다 흩어진다.

### Option C: 메시지 큐 워커

- 설명: 예선처럼 Kafka 이벤트로 받아 결과를 이벤트로 돌려준다.
- 장점: 재시도와 부하 흡수에 강하다.
- 단점 및 위험: 본선 MVP에 브로커 운영이 추가된다. 현재 팀 구성에 브로커 담당이 없다.

### Option D: MCP 서버

- 설명: 에이전트가 도구로 호출한다.
- 장점: Agent SDK 기반 에이전트에 자연스럽게 붙는다.
- 단점 및 위험: CI나 일반 백엔드에서 부르려면 HTTP가 따로 필요하다.

## Decision

- 선택: Option A
- 결정 이유: 호출 주체가 미정인 지금 가장 넓게 붙는다. 에이전트가 쓰게 되면 HTTP를 감싼 얇은 도구만 추가하면 된다.
- 감수한 트레이드오프: 서비스가 죽으면 판단도 멈춘다. 큐가 없어 부하가 몰리면 호출자가 재시도해야 한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 호출자가 파이썬 하나뿐이면 Option B, 호출이 대부분 비동기 이벤트이면 Option C를 다시 본다.

## Follow-up

- 오늘 회의에서 호출 주체와 시점을 확정한다.
- 에이전트가 호출자로 정해지면 도구 어댑터를 추가한다.
