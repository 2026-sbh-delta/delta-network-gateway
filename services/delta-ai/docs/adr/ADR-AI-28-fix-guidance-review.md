# ADR-AI-28: 보안 패치의 생성과 판단을 어떻게 나누고 기준을 어떻게 공유할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 확정 전까지 승인된 결정이 아니다. 구현하지 않았고, 정준우 님과 합의하기 전이다. 처음에 `feat/jenkins-local` 의 ADR-AI-26(`78f5dd2`)으로 썼으나 온프레미스 ADR 과 번호가 겹쳐 28 로 옮겼다.

## Context

- 결정할 질문: 코드 보안 패치를 준우 님 서비스가 만들 때, delta-ai 의 판단 기준을 어떻게 전달하고 배포 전 최종 판정은 어디서 할 것인가?
- 현재 문제와 배경:
  - PR #3 으로 `code_security` 가 delta-ai 에서 빠졌다(ADR-AI-14·15 폐기). 코드 보안은 준우 님 담당이다.
  - 그래서 Jenkins 수정 루프(`fix_loop.py`)의 패치 출처가 사라졌고, 패치 뒤 판정을 내리는 곳도 없다.
  - 승인된 규칙 후보는 쓰이는 곳이 없다. `store.active_rules()` 를 호출하는 코드가 `main` 에 없고, README 는 적용 지점을 SAST 쪽에서 정한다고 적었다.
  - `delta-dast` 의 `/fix` 는 delta-ai 문서를 읽지 않는다. 기준은 `FIXER_PROMPT` 에 따로 적혀 있다.
- 2026-11-02 `/fix` 시험 결과(`sample-target`, 실제 Claude):
  - 패치 생성 26초, `app/board.py` 한 파일 수정, `git apply --check` 통과.
  - 패치 요약에 `comments.py` 는 읽지도 고치지도 않았다고 적혀 있다. 같은 취약점이 다른 경로에 남았는지 확인하는 단계가 없다.
  - `scenario=fixed` 재검증은 실습 게시판의 이스케이프 분기를 켤 뿐 **실제 패치를 시험하지 않는다.**
  - 지금 범위는 CWE-79 와 등록된 대상뿐이다.
- 11/02 main 에 들어온 준우 님 설계(PR #4)로 달라진 점:
  - SAST 설계는 수정안 생성을 범위 밖으로 두고 DAST 서비스가 맡는다고 적었다. 패치 주체는 `/fix` 로 유지된다.
  - 스테이징 도구 설계(`deploy(run_id, image) → url`)가 패치 빌드를 띄울 후보다. 다만 코드는 main 밖 브랜치이고 실제 Apply 전이며, DAST 에 스테이징 주소를 등록하는 API 는 아직 없다.
  - 두 설계는 상위 관리 에이전트가 호출한다고 전제한다. 아래 흐름의 Jenkins 자리는 구동 주체 결정(ADR-AI-27)에 따라 바뀔 수 있다.
- ADR-AI-27 과의 관계: 27 은 DAST 결과 판정(`dast_verification`)을 정했고 `/fix` 패치 흐름은 정하지 않았다. 이 ADR 이 그 빈칸을 다룬다. `fix_review` 는 27 의 상태 판정 규칙을 그대로 쓰고 패치 빌드 일치, 테스트, 변경 파일 조건을 더한다.
- 범위: 패치 생성과 판단의 경계, 기준 전달 방식, 증거 형식을 다룬다. SAST 재설계와 탐지 방식은 다루지 않는다.

## Decision Drivers

1. 패치를 만든 쪽의 자기 보고만으로 배포되지 않는다.
2. 담당 경계를 지킨다. PR #3 으로 나눈 코드를 다시 합치지 않는다.
3. 기준이 한 곳에 있어 두 서비스가 따로 고치지 않는다.
4. 판정은 재현할 수 있어야 한다(ADR-AI-04). LLM 은 판정하지 않는다.
5. 본선(11/07)까지 구현할 수 있어야 한다.

## Considered Options

### Option A: 준우 님 서비스가 전부 처리하고 결과만 보고

- 설명: 패치와 재검증, 판단까지 그쪽에서 하고, 이쪽은 보고를 읽고 적용한다.
- 장점: 경계가 가장 단순하고 합의할 것이 적다.
- 단점 및 위험: 기준이 코드에 없어 매번 사람이 읽어야 한다. 만든 쪽이 통과도 정한다.

### Option B: 판단 코드를 공유

- 설명: delta-ai 판단 모듈을 라이브러리로 만들어 `delta-dast` 가 가져다 쓴다.
- 장점: 판단 로직이 한 벌이고 호출 없이 쓸 수 있다.
- 단점 및 위험: 두 서비스의 배포와 소유권이 묶인다. PR #3 의 분리를 되돌리고, 본선 직전 충돌 위험이 있다.

### Option C: 기준은 공유하고, 증거로 판정 (권고)

- 설명: delta-ai 는 기준 문서와 통과 조건을 제공한다. 준우 님 서비스는 그 기준을 참고해 패치를 만들고, 재검증 증거를 낸다. delta-ai 는 증거만 코드로 판정한다.
- 장점: 코드를 합치지 않고 기준을 공유한다. 승인 규칙을 쓸 자리가 생긴다. 판정이 재현된다.
- 단점 및 위험: 증거 형식을 합의해야 한다. 패치한 코드를 띄워 재검증하는 경로가 필요하다.

### Option D: delta-ai 가 패치 내용을 다시 분석

- 설명: `code_security` 처럼 LLM 이 코드를 읽어 패치가 맞는지 판단한다.
- 장점: 재검증이 없어도 의견을 낼 수 있다.
- 단점 및 위험: PR #3 과 정면으로 충돌하고 코드 보안 판단이 두 곳으로 갈라진다. LLM 의견은 실측 증거를 대신하지 못한다.

## Decision

- 선택: Option C 권고.

### 흐름

```text
delta-ai 기준 문서 ──(직접 가이드)──▶ delta-dast /fix → 패치 + 추적 정보 (준우 님)
                                            │
Jenkins: 샌드박스 적용 → 테스트 → 패치 빌드 배포 → DAST 재검증
                                            │ 증거 묶음
                                            ▼
delta-ai `fix_review`: 코드로 판정 (간접 가이드)
   ├─ pass        → 사람 승인 → 카나리 배포
   ├─ fix         → 기각 사유를 /fix 입력으로 전달, 재시도 (최대 2회)
   └─ needs_human → 멈춘다
```

### 역할

| 담당 | 맡는 일 | 하지 않는 일 |
|---|---|---|
| 준우 님 (`delta-dast`) | 재현, 패치 생성, 패치 빌드 재검증 | 최종 통과 판정 |
| 김연재 (`delta-ai`) | 기준 문서, 통과 조건, `fix_review` 판정 | 패치 생성, 코드 취약 여부 판단 |
| Jenkins | 적용, 테스트, 변경 파일 측정, 호출 순서 | 판단 |
| 사람 | 패치 승인, 규칙 후보 승인 | |

### 직접 가이드: 기준 전달

1단계(본선 최소): `delta-dast` 가 `services/delta-ai/knowledge/rules/security/CWE-*.md` 를 읽어 `FIXER_PROMPT` 뒤에 붙이고, 사용한 문서의 해시를 결과에 넣는다. 새 API 는 없다.

- 같은 모노레포에 있어 지금도 읽을 수 있다. CWE-78·79·89 문서가 있고 CWE-79 의 고치는 법은 `FIXER_PROMPT` 의 인코딩 규칙과 같은 방향이다.
- 문서에 `## 금지 변경`, `## 제출 증거` 절을 추가한다. 내용은 김연재가 쓴다.
- 문서가 없는 CWE 는 패치를 만들 수는 있어도 `fix_review` 에서 `NO_EVIDENCE_DOC` 로 사람에게 넘긴다.

2단계(시간이 남으면): 승인 규칙까지 전달하는 `GET /v1/guidance?cwe=` 를 추가한다. 이때 승인된 규칙이 처음으로 쓰이게 된다.

- 지금 토큰 하나로 판단과 규칙 승인을 모두 할 수 있다(ADR-AI-20). `delta-dast` 에 이 토큰을 주면 자기 입력이 될 규칙을 직접 승인할 수 있으므로, 읽기 전용 토큰을 먼저 나눈다.
- 승인 규칙은 보고서에서 나온 값이므로 시스템 프롬프트가 아니라 데이터로 넘긴다.

### 간접 가이드: `fix_review` 통과 조건

입력은 증거 묶음이고, 코드를 읽지 않으며 LLM 도 판정에 쓰지 않는다. SARIF 입력과 코드 패치 생성을 되살리는 것이 아니다(ADR-AI-14·15 유지).

| 조건 | 출처 | 어긋날 때 |
|---|---|---|
| 수정 전 `REPRODUCED` | DAST 실행 기록 | `needs_human` |
| **패치 빌드**에서 `NOT_REPRODUCED` | DAST 재검증 + 빌드 식별자 일치 | 재현되면 `fix` / `BLOCKED` 는 `needs_human` |
| 재검증 대상 빌드가 패치 빌드와 같음 | Jenkins 빌드 식별자 | `needs_human` |
| 테스트 통과 | Jenkins 샌드박스 실행 | `fix` |
| 금지 파일 미변경(테스트, 검사 설정, CI) | Jenkins 가 패치에서 직접 측정 | `needs_human` (`AUTOFIX_FORBIDDEN`) |
| 기준 문서 해시가 현재와 같음 | `/fix` 결과와 delta-ai 비교 | `needs_human` |
| 증거 누락 | | `needs_human` (`EVIDENCE_UNKNOWN`) |

- 테스트와 변경 파일은 Jenkins 가 직접 측정한다. 패치를 만든 쪽의 보고를 쓰지 않는다.
- `DAST` 판정은 Playwright 실행 결과이므로 증거로 쓴다. 패치 요약 같은 LLM 서술은 표시만 하고 판정에 넣지 않는다.

### 실패 처리

- 기준 문서를 못 읽으면 패치는 만들 수 있지만 해시가 없으므로 `fix_review` 는 `pass` 를 주지 않는다.
- `fix_review` 호출이 실패하면 통과로 보지 않는다(ADR-AI-25 와 같음).
- 재시도는 최대 2회다. 넘으면 사람에게 넘긴다.

### 결정 이유와 트레이드오프

- 결정 이유: 문서 참조만으로는 LLM 이 기준을 따랐는지 보장되지 않고, 사후 판정만으로는 시도가 낭비된다. 둘을 함께 쓰되 구속력은 판정 쪽에만 둔다.
- 감수한 트레이드오프:
  - 패치 빌드 배포 경로가 준비되지 않으면 `fix_review` 는 `pass` 를 낼 수 없다.
  - DAST 가 재현한 경로만 증명한다. 재현하지 않은 다른 출력 지점의 같은 취약점은 놓칠 수 있다.
  - 지금은 CWE-79 만 흐름 전체를 시연할 수 있다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 패치 주체가 `/fix` 가 아니게 되거나, 패치 빌드 재검증을 본선까지 만들 수 없을 때.

## 합의가 필요한 것 (정준우 님)

1. 패치 빌드를 스테이징 도구로 띄워 재검증할지, DAST 대상 등록 API 를 누가 언제 만들지.
2. `FIXER_PROMPT` 에 기준 문서를 붙이는 방식과 해시를 결과에 넣는 방식.
3. 재검증 결과에 빌드 식별자를 넣는 형식. SAST·스테이징과 같은 `run_id` 를 쓰면 되는지.
4. 시연 대상을 XSS `sample-target` 으로 맞출지.

## Follow-up

- 합의 후 `fix_review` kind 와 평가 사례를 추가한다.
- `fix_loop.py` 의 파일 제한을 바꾼다. 스캐너가 지목한 파일만 허용하는 대신, 금지 파일을 막고 나머지는 판정 단계에서 본다.
- `delta-dast` 를 서버에 올리기 전에 `/fix` 인증을 정한다. 지금은 `127.0.0.1` 바인드에 의존하고 쓰기 토큰을 인증 없는 `/api/config` 에서 받을 수 있다.
- 승인 후 `docs/adr/README.md` 목록과 delta-ai README 의 현재 한계를 고친다.
