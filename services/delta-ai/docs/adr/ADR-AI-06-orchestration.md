# ADR-AI-06: 판단 흐름을 어떤 프레임워크로 구성할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 판단 서비스에 LangGraph나 Agent SDK를 쓸 것인가?
- 현재 문제와 배경: 예선은 LangGraph를 썼다. 본선 MVP는 호출마다 규칙 → 근거 → LLM 1회 → 코드 판정으로 끝나며 내부 반복이 없다. 다만 Notion OPTION C에는 Agents SDK 활용이 목표로 적혀 있다. 11/01 취약점 점검 에이전트 담당과 확인한 결과, 판단 서비스는 LangGraph를 쓰지 않고 에이전트 쪽도 LangGraph 없이 개발한다.
- 범위: 판단 서비스 내부만 다룬다. 점검 에이전트의 프레임워크는 담당자가 정한다. 발표용 진행 그래프는 ADR-AI-24에서 다룬다.

## Decision Drivers

1. 흐름이 단순한 만큼 코드도 단순하다.
2. 입력에 조종될 수 있는 자율 도구를 판단 경로에 넣지 않는다.
3. 심사에서 발전된 AI 기능 활용을 보여 줄 수 있다.

## Considered Options

### Option A: 일반 async 함수 (현재 구현)

- 설명: `service.assess()`가 순서대로 호출한다.
- 장점: 의존성이 없고 읽기 쉽다. 경로가 고정이라 테스트가 쉽다.
- 단점 및 위험: 재개, 체크포인트, 시각화를 직접 만들어야 한다. 그 자체로는 Agent SDK 활용을 보여 주지 못한다.

### Option B: LangGraph

- 설명: 예선의 그래프를 다시 쓴다.
- 장점: 사람 승인 후 재개와 체크포인트에 강하다. 팀에 경험이 있다.
- 단점 및 위험: 재시도 루프를 호출자로 옮긴 지금은 분기가 거의 없어 이득이 작다. 저장소 설정이 추가된다.

### Option C: Claude Agent SDK

- 설명: Claude Code의 도구와 루프를 라이브러리로 쓴다.
- 장점: 파일 수정과 명령 실행이 이미 있어 샌드박스 수정에 잘 맞는다.
- 단점 및 위험: 판단 경로에서 모델이 도구를 고르면 입력 글에 조종될 여지가 커진다. 비용과 지연을 예측하기 어렵다.

### Option D: Managed Agents·Bedrock Agents

- 설명: 호스팅 서비스가 루프를 실행한다.
- 장점: 실행 환경 운영 부담이 줄어든다.
- 단점 및 위험: 판단 서비스에 필요 없는 범위다. 특정 제공자에 묶이므로 Beyond Lock-In 설명과 충돌할 수 있다. 세부 비교는 하지 않았다.

## Decision

- 선택: 판단 서비스는 Option A. Agent SDK는 샌드박스 수정 에이전트에 쓰는 것을 권고한다.
- 결정 이유: 판단은 단일 호출로 충분하고 자율 도구가 오히려 위험이다. 자율성이 필요한 곳은 실행 쪽이다.
- 감수한 트레이드오프: 판단 서비스만 보면 "에이전트"가 아니다. 예선의 사람 재개 흐름도 가져오지 않아, 재개는 호출자가 수정 후 다시 호출하는 방식이 된다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 서비스 안에서 여러 단계의 LLM 판단이나 대기 후 재개가 필요해지면 Option B를 다시 본다. 도입한다면 점검 에이전트 담당에게 먼저 알린다.

## Follow-up

- 심사 기준에서 Agents SDK 활용이 어떻게 평가되는지 원문을 확인한다.
- 점검 에이전트 담당자가 Agent SDK를 쓸지 확인한다. LangGraph를 쓰지 않는 것만 확인했다.
