# ADR-AI-15: LLM 코드 패치를 어떤 형식으로 받고 검증할 것인가

> 상태: 폐기 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.
>
> 2026-11-02: 코드 보안 판단(`code_security`)을 delta-ai에서 뺐다. SAST는 별도 서비스가 SARIF와 코드 흐름으로 다시 설계한다. 이 문서는 결정 기록으로만 남긴다.

## Context

- 결정할 질문: LLM이 만든 코드 수정을 어떤 형식으로 받아 어떻게 믿을 수 있게 만들 것인가?
- 현재 문제와 배경: 실제 Claude 평가에서 줄 번호가 틀린 diff와 같은 줄을 따로 고쳐 충돌하는 diff가 나왔다. 검사를 통과해도 `git apply`에서 실패했다.
- 범위: 패치 형식과 적용 전 검증을 다룬다. 샌드박스 적용은 ADR-AI-05에서 다룬다.

## Decision Drivers

1. 돌려준 패치는 원본에 반드시 적용된다.
2. 수정 범위가 지적한 파일과 크기를 넘지 않는다.
3. 표준 도구로 적용할 수 있다.

## Considered Options

### Option A: 서버가 diff를 다시 생성 (현재 구현)

- 설명: LLM diff에서 지울 줄과 넣을 줄만 읽어 원본에 적용하고, 그 결과로 서버가 unified diff를 다시 만든다. 파일당 하나만 받고 다른 파일, 비밀 값, 큰 변경(4000자, 40줄 초과)은 거절한다.
- 장점: 줄 번호 오류가 사라지고 `git apply`에 맞는 결과가 나온다. 호출자는 표준 형식을 받는다.
- 단점 및 위험: hunk 파싱 코드를 직접 유지한다. CRLF나 끝 줄바꿈이 없는 파일은 사람에게 넘긴다. 원본 파일을 보내지 않으면 패치가 없다.

### Option B: LLM diff 그대로 전달

- 설명: 형식만 검사해 전달한다.
- 장점: 코드가 가장 적다.
- 단점 및 위험: 실제로 적용 실패가 났다. 시연 중 깨질 수 있어 기각한다.

### Option C: 찾기·바꾸기 블록

- 설명: LLM이 `old`, `new` 문자열을 구조화 출력으로 낸다.
- 장점: diff 문법 오류가 없고 서버 파싱이 단순해진다. 서버는 어차피 diff를 다시 만든다.
- 단점 및 위험: 프롬프트와 출력 스키마를 바꾸고 실제 평가를 다시 돌려야 한다. 비용이 든다.

### Option D: 파일 전체 교체

- 설명: 수정한 파일 전체를 돌려받는다.
- 장점: 적용이 항상 된다.
- 단점 및 위험: 출력 토큰이 커지고 범위 밖 변경을 찾기 어렵다.

## Decision

- 선택: Option A 유지. 패치 실패가 데모 앱에서 다시 나오면 Option C로 바꾼다.
- 결정 이유: 실제 실패를 고친 뒤 `git apply`와 Semgrep 재검사까지 확인한 방식이다. 지금 호출 계약을 그대로 둔다.
- 감수한 트레이드오프: 적용 가능성만 보장하며 동작까지 보장하지 않는다. 서비스는 컴파일이나 테스트를 돌리지 않으므로 샌드박스 실행이 필수다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 정상 패치가 게이트에 자주 걸리거나 데모 앱이 CRLF를 쓰면 다시 본다.

## Follow-up

- 샌드박스에서 패치 적용, 테스트, 재스캔, 재호출 순서를 에이전트 담당과 맞춘다.
