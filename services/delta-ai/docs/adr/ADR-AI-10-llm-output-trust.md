# ADR-AI-10: LLM 출력을 어떻게 검증할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: LLM 응답의 형식과 내용을 어디까지 믿을 것인가?
- 현재 문제와 배경: LLM은 없는 근거를 인용하거나 없는 항목을 만들 수 있다. 입력 글에 조종될 수도 있다.
- 범위: 설명, 분류, 인용의 검증을 다룬다. 패치 검증은 ADR-AI-15에서 다룬다.

## Decision Drivers

1. 없는 근거가 사용자에게 보이지 않는다.
2. 실패하면 안전한 쪽으로 간다.
3. 구현이 단순하다.

## Considered Options

### Option A: 구조화 출력, 전체 검증, 실패 시 폐기 (현재 구현)

- 설명: JSON 스키마를 강제하고 Pydantic으로 다시 검사한다. `finding_id` 집합이 정확히 맞아야 하고 인용은 받은 근거 안에 있어야 한다. 어긋나면 출력 전체를 버리고 `LLM_OUTPUT_INVALID`로 사람에게 넘긴다.
- 장점: 없는 근거가 결과에 섞이지 않는다. 판정 로직이 단순하다.
- 단점 및 위험: 항목 하나의 잘못으로 나머지 정상 설명까지 버린다. 재시도가 없어 일시적 실수도 사람 확인이 된다.

### Option B: 항목별로 부분 채택

- 설명: 맞는 항목만 쓰고 틀린 항목만 규칙 설명으로 대체한다.
- 장점: LLM 결과를 더 많이 살린다.
- 단점 및 위험: 일부가 틀린 응답이면 나머지도 믿기 어렵다. 부분 성공 상태를 호출자에게 설명해야 한다.

### Option C: 실패 시 1회 재시도

- 설명: 검증 오류를 알려 주고 다시 요청한다.
- 장점: 사람 확인이 줄어든다.
- 단점 및 위험: 지연과 비용이 늘고 입력의 지시문을 재시도마다 더 반영할 위험이 있다.

### Option D: 자유 형식 응답 후 파싱

- 설명: 일반 텍스트를 정규식으로 읽는다.
- 장점: 모델과 경로 제약이 없다.
- 단점 및 위험: 형식이 깨지기 쉽다. 구조화 출력을 쓸 수 있으므로 택할 이유가 없다.

## Decision

- 선택: Option A
- 결정 이유: 보안 판단에서는 조금 덜 친절해도 잘못된 근거가 나오지 않는 편이 낫다.
- 감수한 트레이드오프: LLM이 조금만 틀려도 사람 확인이 늘어 자동화율이 내려간다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 실제 호출에서 `LLM_OUTPUT_INVALID`가 자주 나오면 Option C를 검토한다.

## Follow-up

- 데모 앱 평가에서 `LLM_OUTPUT_INVALID` 비율을 기록한다.
