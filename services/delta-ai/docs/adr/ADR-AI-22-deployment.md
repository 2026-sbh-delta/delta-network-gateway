# ADR-AI-22: 판단 서비스를 어디에 어떻게 배포할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다. **아직 구현하지 않았다.**

## Context

- 결정할 질문: 판단 서비스를 어떤 형태로 어디에 띄울 것인가?
- 현재 문제와 배경: 지금은 로컬 `uvicorn`으로만 돈다. Dockerfile이 없고 공유 레포에도 없다. 플랫폼의 위치와 CI/CD 도구는 미정이다.
- 범위: 판단 서비스 배포만 다룬다. 시연 대상 앱의 이전은 다루지 않는다.

## Decision Drivers

1. 시연 대상 앱을 옮기는 동안 판단 서비스는 영향을 받지 않는다.
2. 다른 팀원이 쉽게 실행한다.
3. 시연 중 LLM 호출과 규칙 저장이 안정적이다.

## Considered Options

### Option A: 컨테이너 1개를 플랫폼 쪽에 배포

- 설명: 이미지를 만들어 관리 플랫폼과 같은 곳에 인스턴스 1개와 볼륨으로 띄운다.
- 장점: 실행 환경이 어디든 같다. 앱의 이전 대상과 분리할 수 있다. JSON 저장소 전제와 맞는다.
- 단점 및 위험: 단일 인스턴스라 죽으면 판단이 멈춘다. 호출 경로와 시크릿 주입을 준비해야 한다.

### Option B: 서버리스 함수

- 설명: Lambda나 Cloud Run 함수로 띄운다.
- 장점: 쓰지 않을 때 비용이 작다.
- 단점 및 위험: 파일 저장소를 쓸 수 없어 ADR-AI-19를 먼저 바꿔야 한다. 콜드 스타트와 시간 제한 확인이 필요하다. 클라우드에 묶인다.

### Option C: 여러 인스턴스 HA

- 설명: 쿠버네티스에 여러 인스턴스로 띄운다.
- 장점: 장애에 강하다.
- 단점 및 위험: 외부 저장소가 먼저 필요하다. 현재 MVP에 과하다.

### Option D: 시연까지 로컬 노트북

- 설명: 터널이나 내부망으로 노트북의 서비스를 호출한다.
- 장점: 준비가 거의 없다.
- 단점 및 위험: 노트북과 현장 네트워크가 단일 장애점이다. 배포 품질 설명이 약하다.

## Decision

- 선택: Option A 권고. 통합 전까지는 Option D로 연동을 시험한다.
- 결정 이유: 앱 이전과 분리되고 저장소 교체 없이 가능하다.
- 감수한 트레이드오프: 단일 인스턴스 장애를 받아들인다. 판단 서비스 자체의 무중단은 시연 범위에서 제외한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 플랫폼 위치가 정해지거나 판단 서비스 HA를 심사 항목으로 보면 다시 본다.

## Follow-up

- 공유 레포가 생기면 Dockerfile을 추가하고 `uv.lock`으로 빌드한다.
- API 키와 서비스 토큰의 주입 방식을 플랫폼 담당과 맞춘다.
- `delta-ai`를 먼저 git으로 백업한다. 지금은 로컬 복사본이 유일하다.
