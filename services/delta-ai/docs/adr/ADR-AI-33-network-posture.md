# ADR-AI-33: 격리 수준이 다른 환경을 어떻게 구분하고 제안할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 확정 전까지 승인된 결정이 아니다. 코드는 브랜치 `feat/onprem-integration` 에 있다.

## Context

- 결정할 질문: VLAN·방화벽·파드 정책이 있는 환경과 공유 네트워크에 그대로 붙은 환경을 서비스가 어떻게 구분하고, 각각 무엇을 제안할 것인가?
- 현재 문제와 배경: 방화벽 룰을 읽지 못하는 노드는 `PAR-NET-003` 점검 자체가 빠져, 위험한 환경일수록 점검 항목이 보이지 않았다. NetworkPolicy는 입력도 규칙도 없었다.
- 범위: 태세 판정과 제안을 다룬다. 온프레미스 증거 입력 전반은 [ADR-AI-26](ADR-AI-26-onprem-runtime.md)에서 다룬다.

## Decision Drivers

1. 신고한 설정이 아니라 실제로 막히는지로 판단한다.
2. 측정하지 못한 것을 안전하다고 표시하지 않는다.
3. 그 환경의 운영자가 실제로 할 수 있는 조치만 제안한다.
4. 남의 네트워크를 스캔하지 않는다.

## Considered Options

### Option A: 실측 기반 3계층 태세

- 설명: 네트워크, 노드, 클러스터를 연결 시험과 정책으로 나눠 코드가 `isolated`, `partial`, `open`, `unknown` 으로 판정한다. 제안은 `upstream_firewall` 값으로 고른다.
- 장점: 설정이 있어도 실제로 뚫린 경우를 잡고, 개방 환경에도 점검 항목이 남는다.
- 단점 및 위험: 시험 지점과 대상을 호출자가 정해야 한다. 판정 범위가 그 지점의 결과로 제한된다.

### Option B: 운영자가 환경 유형을 신고

- 설명: 입력에 "VLAN 있음"을 받아 제안만 나눈다.
- 장점: 구현이 간단하다.
- 단점 및 위험: 설정이 실제로 집행되는지 알 수 없다. 이번 시험의 NodePort 노출을 놓친다.

### Option C: 방화벽 룰 정적 분석만 사용

- 설명: 기존 `PAR-NET-003` 을 확장한다.
- 장점: 시험 트래픽이 필요 없다.
- 단점 및 위험: 공유기만 있는 환경은 룰을 읽을 수 없어 판단이 불가능하다. 같은 VLAN 안의 이동도 보이지 않는다.

### Option D: 주변 네트워크 스캔

- 설명: 노드가 속한 대역을 훑어 노출을 찾는다.
- 장점: 많은 경로를 자동으로 찾는다.
- 단점 및 위험: 공유망에서는 허가 없는 스캔이 된다. 검토 즉시 제외했다.

## Decision

- 권고: Option A.
- 양성 대조: 열려 있어야 할 경로가 실패하면 닫힘 결과를 믿지 않고 `unknown` 으로 둔다.
- 노드 격리: 바깥 지점에서 건 `inbound_probes` 가 있어야 인정한다. 호스트 방화벽 기본 거부만으로는 인정하지 않는다.
- 제안: 관리 가능한 환경에는 VLAN과 방화벽 룰을, 관리할 수 없는 환경에는 호스트 방화벽과 터널을 제안한다. 모르면 둘 다 제시한다.
- 적용: 사람이 한다. 제안의 `autofix` 는 금지이고 NetworkPolicy는 초안까지만 만든다.

## 실측으로 바뀐 판단

같은 VLAN에 VM 201을 추가해 평면 네트워크를 재현했다. 같은 VLAN 안의 통신은 방화벽을 거치지 않아 룰을 바꾸지 않아도 된다.

| 환경과 상태 | 네트워크 | 노드 | 클러스터 | 전체 |
|---|---|---|---|---|
| VM 201, 보호 없음 | 열림 | 열림 | 열림 | `open` |
| VM 201, 서비스 제안 적용 | 격리 | 열림 (22, NodePort 2개) | 격리 | `partial` |
| VM 200, VLAN과 수신 정책만 | 격리 | 열림 (22, 6443, 10250, NodePort 2개) | 격리 | `partial` |
| VM 200, 호스트 방화벽과 NodePort 차단 추가 | 격리 | 격리 | 격리 | `isolated` |

- 첫 `isolated` 철회: 처음에는 VM 200을 `isolated` 로 판정했지만, 옆 VM에서 시험하니 관리 포트와 NodePort가 열려 있었다. 이 경험으로 노드 격리 조건을 바꿨다.
- 게이트웨이만 시험한 경우: 격리로 잘못 인정하는 버그를 찾아 고쳤고, 수집기 출력으로 재현하는 테스트를 추가했다.
- NodePort: UFW INPUT 룰로는 막히지 않아 `mangle/PREROUTING` 에서 차단했다.
- 유지 확인: 적용과 재부팅 후에도 인그레스 200, 앱에서 DB로 가는 연결이 유지됐다.
- 재수집 결과: 11/02 시연 콘솔용 재수집에서는 VM 201 → VM 200 양성 대조(포트 80)가 실패해 노드와 전체 태세가 `unknown` 이다. 같은 VLAN인데 ping도 실패하고 원인은 찾지 못했다. 위 표의 `isolated` 는 그 전 측정값이다.

## Consequences

- 긍정: 같은 앱이 환경에 따라 다른 판정과 제안을 받고, 조치 후 재측정으로 개선되는 것을 보여 줄 수 있다.
- 부정: `isolated` 는 VM 201 한 지점 기준이고 인터넷 쪽 시험은 하지 않았다. 호스트 방화벽은 iptables 기본 정책만 읽어 nftables 전용 룰은 허용으로 보인다. 태세가 `isolated` 여도 이미지 취약점 등 다른 항목 때문에 전체 판정은 `needs_human` 이다.
- 운영 영향: VM 200의 6443은 바깥에서 막혀 있어, Jenkins나 Argo 같은 외부 배포 도구를 붙이면 출발지 허용을 추가해야 한다.
- 시험 조건: 시험 지점 VM 201이 자기 ufw로 나가는 연결을 막으면 양성 대조가 실패해 `unknown` 이 나온다. VM 200을 시험할 때는 끄고 끝나면 다시 켠다.
- 후속 작업: 팀 결정, 수집기 호출 주체와 주기, 인터넷 쪽 지점 추가 여부.

## Affected Components

## Security & Compliance

- 설정에 적은 대상과 기본 게이트웨이만 시험하고 주변 기기를 스캔하지 않는다.
- 결과와 제안에는 시험 대상 주소가 들어간다. 공개 자료에 쓸 때는 이름으로 바꾼다.
