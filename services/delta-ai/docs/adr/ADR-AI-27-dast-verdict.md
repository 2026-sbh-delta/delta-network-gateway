# ADR-AI-27: DAST 결과를 누가 판정하고 전체 흐름은 누가 구동할 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 구동 주체는 김연재 결정(Jenkins, 관리 에이전트는 우선 기각)이고 준우 님 설계와 맞추는 일이 남았다. 판정은 로컬 시연으로만 구현·검증했다. `feat/jenkins-on-main` 의 역할 경계 초안(옛 27)을 이 문서로 합쳤다.

## Context

- 결정할 질문: DAST 결과로 배포를 멈출지 누가 정하고, 온프레미스 증거·DAST·배포로 이어지는 전체 흐름은 누가 구동할 것인가?
- 배경: `services/delta-dast`(Claude Agent SDK·Playwright, 현재 XSS)가 main 에 들어왔고 `code_security` 는 PR #3 으로 delta-ai 에서 빠졌다. `delta-dast` 와 `delta-ai` 는 서로 호출하지 않았다.
- 배경: 11/01 회의에서 Langchain 통합 조사를 김연재가 맡았다. 같은 날 판단 서비스와 점검 에이전트 모두 랭그래프 없이 개발하기로 Slack 에서 정리했다.
- 배경: 11/02 PR #4 로 main 에 들어온 준우 님의 SAST·스테이징 설계는 **상위 관리 에이전트가 각 단계를 도구로 호출**하는 구조를 전제한다. 아래 권고의 Jenkins 구동과 다르므로 합의가 필요하다.
- 범위: 구성 요소의 역할과 공유 방식을 다룬다. 보안 패치의 생성·판정 경계는 [ADR-AI-28](ADR-AI-28-fix-guidance-review.md)에서 다룬다.

## Decision Drivers

1. 점검을 수행한 쪽이 자기 결과의 통과를 정하지 않는다.
2. 판정은 재현할 수 있어야 하고(ADR-AI-04), 결과를 모르면 통과로 보지 않는다.
3. 담당별로 독립 배포할 수 있다. PR #3 의 분리를 되돌리지 않는다.
4. 본선(11/07)까지 구현할 수 있고 준우 님 서비스 변경을 최소화한다.

## Considered Options

### Option A: Jenkins 구동, DAST 관측, delta-ai 판정 (`dast_verification`)

- 장점: 실행과 판단이 분리되고(ADR-AI-05) 지금 코드로 이어진다. DAST 코드를 바꾸지 않고 API 결과만 받으며 기존 사람 확인·사유 체계를 그대로 쓴다.
- 단점: 호출자가 결과를 옮겨야 한다. 분기 로직이 Jenkinsfile 에 쌓인다.

### Option B: 관리 AI 에이전트가 각 단계를 도구로 호출

- 설명: SAST·스테이징 설계의 전제다.
- 장점: AI 흐름이 한곳에 모이고 도구 정의(`GET /v1/tools`)를 그대로 쓸 수 있다.
- 단점: 에이전트의 담당과 구현이 아직 없고, 실행 순서가 LLM 에 달리면 판정 재현이 어려워진다.

### Option C: LangGraph 로 전체 오케스트레이션

- 장점: 상태 저장과 재개를 제공한다.
- 단점: Jenkins 와 역할이 겹치고 11/01 합의를 되돌리며, 남은 기간에 비해 도입 비용이 크다.

### Option D: DAST 가 배포 여부까지 판정

- 장점: 호출이 한 번으로 끝난다.
- 단점: 판정 기준이 두 곳으로 나뉜다.

### Option E: 판단 로직을 DAST 에 공유 라이브러리로 넣기

- 장점: 네트워크 호출이 없다.
- 단점: 배포 시점이 묶이고 ADR-AI-01 의 HTTP 통합과 어긋난다.

## Decision

- 선택: Option A. 전체 흐름은 Jenkins 가 구동하고 관리 에이전트 구동(Option B)은 우선 기각한다(2026-11-02 김연재). 판정 부분은 `dast_verification` 으로 구현했고 시연으로만 검증했다.
- 판정: `REPRODUCED`·`BLOCKED`·`INCONCLUSIVE` 는 막고, `NOT_REPRODUCED` 만 통과시키며 실측 통제로 기록한다. 대상 전체가 안전하다는 뜻은 아니다. 근거 문서는 `knowledge/rules/dast/` 에 두고 문구는 시험한 절차 범위에서만 쓴다.
- 구동: 시연은 콘솔이 구동한다. DAST 가 루프백 전용이라 Jenkins 컨테이너에서 부를 수 없기 때문이다. 서버에서는 Jenkins 가 구동하고 판정은 delta-ai 에 둔다.
- 판단 문서: 규칙 문서는 `services/delta-ai/knowledge/rules/` 한 곳에 두고 프롬프트는 서비스별로 둔다. 실행 기록은 공통 `run_id` 로 묶는다.
- 피드백 루프: 배포 전에는 탐지 → 패치 → 재검증 → 판정, 배포 중에는 지표 → 자동 롤백 → 실패 분석 → 재발 차단으로 돈다. 새 규칙은 사람 승인 뒤에만 활성화한다(ADR-AI-17).
- 감수한 트레이드오프: 진행 그래프는 단계 이벤트로 따로 만들어야 한다(ADR-AI-24).
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 여러 AI 호출의 재개가 필요해져 Jenkins 분기로 감당하지 못할 때, 또는 Jenkins 로 시연 흐름을 끝까지 잇지 못할 때.

## 아직 정하지 않은 것

- **Jenkins 구동에 맞출 것:** SAST·스테이징 설계는 관리 에이전트 호출을 전제하므로 Jenkins 호출로 맞춘다. DAST 서버 호출 범위(현재 localhost Host 만 허용), 토큰 발급, 스테이징 주소를 실행마다 DAST 대상으로 등록하는 API(스테이징 설계의 남은 일)도 함께 맞춘다.
- **패치 흐름:** `/fix` 패치를 delta-ai 가 검토하는 경로는 만들지 않았다. 시연의 재검증은 준비된 수정 비교군(`fixed`)을 점검한다.
- **대상 일치:** DAST 대상은 실습 게시판이고 배포 대상은 Jenkins 데모 앱(CWE-78)이다. 같은 릴리스를 점검한다고 말할 수 없다.
- **재현할 수 없는 유형:** SAST 설계는 `dast.verifiable = false` 유형에서 SAST 판정을 최종 게이트로 둔다. Driver 1 과 어긋나지 않게 이 판정의 위치를 정한다.
- **`run_id`:** SAST·스테이징 호출에 이미 있으므로 같은 값을 쓰기로 맞춘다.

## Consequences

- delta-ai 계약에 `dast_verification` kind 와 `evidence.dast` 가 늘었고 프롬프트 버전이 `delta-judge-v6` 이 됐다.
- DAST 의 상태 값이 바뀌면 계약 검증에서 요청이 거부된다. 통과로 처리되지 않는다.
