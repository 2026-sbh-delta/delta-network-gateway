# ADR-AI-36: 판단 서비스 장애를 어느 단계에서 잡을 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-02. 로컬 커밋 `5585127` 로 구현·검증했고 푸시·리뷰 전이다.

## Context

- 결정할 질문: 판단 서비스가 죽어 있거나 토큰이 틀릴 때 어느 단계에서 멈출 것인가?
- 현재 문제와 배경: SAST 가 판단 서비스를 부르지 않게 되자 빌드 #59 에서 트래픽 10% 를 옮긴 뒤에야 장애를 알았고 롤백까지 49초가 걸렸다.
- 범위: 배포 시작 시점의 확인만 다룬다. 확인 뒤에 서비스가 죽는 경우는 기존 카나리 단계의 롤백이 막는다.

## Decision Drivers

1. 트래픽을 옮기기 전에 멈춘다.
2. 장애가 통과로 처리되지 않는다.
3. 주소와 토큰을 함께 확인한다.
4. 빌드마다 LLM 비용을 들이지 않는다.

## Considered Options

### Option A: 첫 단계에서 토큰이 필요한 조회 호출

- 설명: `gate_ready.py` 가 `GET /v1/rule-candidates` 를 호출한다. 503·연결 실패만 재시도하고 401·422 는 바로 실패한다.
- 장점: 주소와 토큰을 함께 확인하고 LLM 을 부르지 않는다.
- 단점 및 위험: LLM 자체의 장애는 알 수 없다.

### Option B: 인증 없는 헬스 체크

- 설명: 서비스 생존 여부만 본다.
- 장점: 가장 단순하다.
- 단점 및 위험: 토큰이 틀려도 통과한다.

### Option C: 카나리 롤백에 맡김

- 설명: 코드를 추가하지 않는다.
- 장점: 추가 구현이 없다.
- 단점 및 위험: 판단이 불가능한데도 트래픽 10% 가 새 버전으로 간다.

### Option D: 사전에 LLM 까지 호출

- 설명: 실제 판단을 한 번 호출해 본다.
- 장점: LLM 장애까지 잡는다.
- 단점 및 위험: 빌드마다 비용과 지연이 늘어난다.

## Decision

- 선택: Option A.
- 검증(2026-11-02, 가짜 LLM):

| 빌드 | 시나리오 | 결과 | 확인한 내용 |
|---|---|---|---|
| #61 | `good` | SUCCESS | 첫 배포 |
| #62 | `good` | SUCCESS | 10→50→100% 승격 |
| #63 | `gate-down` | FAILURE | 7초 만에 중단, 트래픽 변경 0회, 버전 62 유지 |
| #64 | `failing-test` | FAILURE | 사전 확인 뒤 테스트에서 중단, 실패 분석 응답 |
| #65 | `bad-canary` | FAILURE | 10% 자동 롤백 |

- 잘못된 토큰으로 직접 실행해 HTTP 401, 종료 코드 30 을 확인했다. 스크립트 테스트 51개와 delta-ai 테스트 85개가 통과했다.
- 감수한 트레이드오프: LLM 장애는 첫 판단 호출까지 알 수 없다. 이때도 통과로 처리되지 않는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 실제 환경에서 LLM 장애로 트래픽 이동 뒤 중단되는 일이 잦을 때.
