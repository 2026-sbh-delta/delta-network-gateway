# Jenkins 배포와 AI 판단 로컬 검증

- 기준일: 2026-11-02 (Asia/Seoul)
- 상태: 로컬 구현·검증 완료. **커밋·푸시·AWS 배포 안 함.** 사용자 지시 "우선 로컬에서 진행"에 따른 시험이며 팀 합의 전이다.
- 실행 방법: [deploy/jenkins-local](../../deploy/jenkins-local/README.md)
- 도구 선택 근거: [ADR-AI-25](../../services/delta-ai/docs/adr/ADR-AI-25-jenkins-gate.md) (제안)

## Ideation

- 문제: 배포 중 나오는 로그·지표·오류를 AI 판단과 연결할 수 있는지 AWS 자원 없이 먼저 확인한다.
- 사용자: 배포 담당(김연재), 시연을 보는 심사위원.
- 성공 기준: 나쁜 배포는 사람 없이 멈추고, 판단 서비스가 죽어도 통과로 처리되지 않으며, LLM 지시문 주입으로 판정이 바뀌지 않는다.
- Scope: Jenkins 파이프라인, `deployment_gate` 판단 종류, HAProxy 대역 위의 카나리.
- Non-goals: 실제 네트워크·서버 배포, 동규 님의 HAProxy 구현, 수정안 자동 적용, Dependency-Check·SonarQube·ZAP.

## Inception

- 판정은 코드가 정한다. LLM 은 설명과 패치만 만든다.
- 근거가 없으면 통과가 아니다. 지표 값·기준·표본이 없거나 표본이 20건 미만이면 `needs_human`(DEP-METRIC-002).
- 롤백은 판단 서비스를 기다리지 않는다. 지표 초과는 파이프라인이 먼저 롤백하고 LLM 은 그 뒤 설명한다.
- 실행과 판단을 분리한다(ADR-AI-05). 판단 서비스는 배포 명령을 실행하지 않는다.

## 검증 중 발견한 것

1. **카나리 비율만큼은 사용자가 오류를 받는다.** 초기 `bad-canary` 빌드 #4 에서 외부 클라이언트가 롤백 전에 HTTP 500 을 4건 받았다. 게이트는 피해를 작게 만들 뿐 없애지 않는다. 시연에서 "오류 0"이라고 말하지 않는다.
2. **지연 게이트가 앱 설정 문제를 잡았다.** 빌드 #10 이 100% 에서 p95 1025ms 로 롤백됐다. 데모 앱의 listen backlog 가 5 였던 것이 원인이고(위 비교), 128 로 올린 뒤 재발하지 않았다. 다만 #10 당시 값을 직접 재현한 것은 아니고 같은 조건의 비교로 확인했다. 실제 서비스 앱에도 같은 점검이 필요하다.
3. **판정 중단을 단계 실패로 보고하던 결함을 고쳤다.** `fix` 판정 뒤 분석이 종료 코드 0 인 `sast` 를 실패로 설명했다. 판정이 중단 사유면 분석을 건너뛴다(#20, #24 로 확인).
4. **Semgrep 이미지 문제.** 최신 `setuptools` 에 `pkg_resources` 가 없어 `setuptools<81` 로 고정했다.
5. **post 실행 순서.** Declarative 는 `always` → `failure` → `cleanup` 순서다. 그래서 롤백은 `always`, 분석은 `failure`, 산출물 보관은 `cleanup` 에 둔다.

## 실패 피드백 루프 평가 (2026-11-02)

결론: **멈추고 설명하는 데까지는 동작한다. 고치고 다시 시도하는 부분은 파이프라인에 없다.** 실제 Claude(`claude-sonnet-5-5`)로 실행했다. 빌드 #27~31 과 별도 평가 스크립트 결과이며, 스크립트는 레포에 넣지 않았다.

| 경로 | 결과 | 근거 |
|---|---|---|
| 취약 코드 → 패치 → 재검사 | 3/3 통과, **단 패치 적용은 평가 스크립트가 했다** | `git apply` 성공, 테스트 OK, Semgrep 1→0건, `fix`→`pass`, 셸 주입 실패. 대조: 원본은 주입 성공, 주석만 추가하면 계속 `fix` |
| 테스트 실패 → 원인 분석 | 동작 | #27 실패 테스트와 파일·줄을 정확히 지목 |
| 카나리 오류 → 원인 분석 | 부분 동작 | #28, #29 롤백은 정상, 분석은 "오류 응답이 문제이나 원인은 알 수 없음". 앱 로그를 판단 서비스에 보내지 않아서다 |
| 같은 실패 재발 방지 | **없음** | #28 에 이어 #29 도 같은 문제를 10% 트래픽에 다시 노출. commit 값도 `local` 고정이다 |
| 보안 보고서 → 규칙 → 다음 검사 | 동작 | 후보 생성·승인 뒤 취약 코드는 CWE-78 로 검출, 안전 코드는 `pass`. 컨테이너 재생성 후에도 규칙 유지 |
| 배포 실패 → 규칙 | **없음** | `feedback_ingest` 는 보안 보고서만 받는다 |
| 로그 지시문 주입 | 방어됨 | `needs_human` 유지, LLM 은 지시문을 분석 대상으로 다룸. 1건만 시험 |
| LLM 호출 실패 | 안전하게 실패 | #30 잘못된 키: 빌드는 실패, 분석은 규칙 문서 내용으로 대체 |
| 카나리 중 판단 서비스 중단 | 안전하게 실패 | #31 10% 판단 불가로 롤백, 기존 버전 유지. **정상 버전도 롤백된다.** 분석은 남지 않는다 |

한계: 패치 시험은 취약점 1종 3회이고 표본이 작다. 평가에서 승인한 시험 규칙이 로컬 볼륨에 남아 있다(`./down.sh --volumes` 로 제거).

## 수정 루프와 재발 차단 구현 (2026-11-02, main 병합 전 코드)

- 수정 루프(`fix_loop.py`): `fix` 판정이면 사본에 패치 적용 → 네트워크 없는 컨테이너에서 테스트 → 원본 설정으로 Semgrep 재검사 → 재판단. 최대 2회. 통과해도 사람 승인 뒤에만 작업 트리에 반영한다.
- 패치 범위: 적용 전후 트리를 비교해 스캐너가 지목한 파일 밖의 변경, 심볼릭 링크 생성을 거절한다.
- 앱 로그: 롤백 전에 카나리 로그 50줄을 남겨 실패 분석에 보낸다.
- 재발 차단(`releases.py`): 코드와 런타임 설정의 해시로 릴리스를 식별한다. 지표 초과로 롤백되면 기록하고, 같은 릴리스는 사람 승인 없이 트래픽을 받지 못한다. 승격에 성공하면 기록을 지운다.

확인하지 못한 것:

- **`good` 승격은 부하 때문에 최종 재확인이 안 됐다.** 같은 코드의 #32 는 SUCCESS 였으나 #45, #50, #52 는 오류율 0 인데 p95 793~1075ms 로 자동 롤백됐다. #52 는 10%·50% 를 통과하고 100% 에서만 초과했고, 안정 버전을 직접 재도 p95 160~665ms 였다. 당시 Mac 은 부하 평균 11~13, 스왑 사용 약 90% 였다. 코드 원인은 찾지 못했고 호스트 부하로 판단하지만, 부하가 낮을 때 다시 확인해야 한다.
- **성공 시 기록 삭제**는 단위 테스트만 통과했고, 실패 기록이 있는 릴리스의 승격 성공은 실행하지 못했다. 부하로 생긴 `good` 기록은 수동으로 지웠다.
- **샌드박스 테스트 실패 경로**는 단위 테스트만 했다. #43 에서 Claude 가 테스트 요구를 읽고 `shell=True` 를 남기는 패치를 내 재판단에서 먼저 멈췄다.
- `low-traffic` 은 같은 릴리스의 실패 기록 때문에 재발 확인에서 멈춰(#48, #51) 표본 부족 경로를 이번 코드로 다시 보지 못했다.

새로 드러난 위험:

- **고정 지연 기준은 느린 서버에서 정상 배포를 되돌린다.** 그 오탐이 실패 기록까지 남겨 다음 배포에 사람 확인을 요구한다. t4g.nano·e2-micro 시연에 그대로 쓰면 위험하다. 카나리와 안정 버전을 같은 구간에서 비교해야 한다.
- 데모 이미지는 `app.py` 만 복사하므로 패치한 `vulnerable.py` 는 실제 실행되지 않는다. 승인한 패치도 원본 소스로 돌아가지 않아 다음 빌드에서 같은 지적이 반복된다.

| #65 | `bad-canary` | FAILURE | 10% 자동 롤백, 서비스는 버전 62 유지 |

잘못된 토큰으로 Jenkins 컨테이너에서 `gate_ready.py` 를 직접 실행해 종료 코드 30 을 확인했다. 스크립트 테스트는 51 통과.

- **확인 못 한 것:** 실제 Claude 호출은 이번에 하지 않았다. 호스트 부하 평균은 12~16 이었고 이번에는 지연 오탐이 없었지만, 고정 기준의 위험은 위 기록과 같다.

## 아직 안 된 것

- `main` 기준 패치 출처 결정. 정하지 않으면 수정 루프를 시연할 수 없다.
- 카나리와 안정 버전 비교, 승인한 패치의 소스 반영(브랜치·PR), 실제 commit SHA 전달(지금은 내용 해시).
- 이벤트는 판단 호출 때만 남긴다. ADR-AI-24 진행 그래프에 쓰려면 단계 시작·종료도 내보내야 한다.
- Dependency-Check, SonarQube, ZAP.
- 사설망·ANF, Jenkins 외부 경로, 실제 서버 메모리, AWS→GCP 교차 배포, ARM/x86, 실제 HAProxy.
- Jenkins 자체의 보안 설정. 로컬 전용 구성이라 서버용으로 다시 만들어야 한다.
