# 사용자 선택 기반 배포와 다중 대상 이전

## 승인과 범위

2026-11-05 사용자가 서비스 등록 시 최초 환경과 VM 사양을 선택하고, 배포 후 다른 환경으로 이전하는 흐름을 요청했다. 이전 대상은 GCP와 온프레미스를 동시에 선택할 수 있다고 확정했고 후속 `go ahead`로 구현을 승인했다. 전용 브랜치 `feat/platform-deployment-targets`, `platform/` 경계를 사용한다. 커밋·PR 전에는 변경 내용과 메시지를 보고한다.

## 설계

- 최초 배포는 AWS·GCP·온프레미스 중 하나다. 클라우드는 지원하는 VM 사양, 온프레미스는 등록 호스트와 앱 자원 한도를 선택한다. 온프레미스에서 새 VM을 만드는 것처럼 표시하지 않는다.
- 등록 정보와 실제 환경을 구분한다. 등록만으로 자원을 만들지 않는다. 성공한 이미지와 해당 대상의 샌드박스 검사 결과를 확인한 뒤 배포 계획을 검토·승인한다.
- 기존 Jenkins의 고객 이미지 빌드 작업과 별도 배포 작업/에이전트를 사용한다. 배포 실행기는 고정된 플랫폼 코드와 검증된 JSON만 받으며 고객 저장소의 Terraform·셸 코드를 실행하지 않는다.
- 클라우드 VM은 플랫폼 전용 Terraform root로 준비한다. 기존 팀 네트워크·VM·Terraform state를 편집하거나 가져오지 않는다. 연결 정보와 권한이 없는 환경은 실행 불가 이유를 표시한다.
- 대상별 실행 결과를 저장하고 실제 자원 식별자·이미지·헬스 체크를 확인한 뒤 환경을 자동 등록한다. GCP와 온프레미스 두 대상 중 하나가 실패해도 나머지 결과와 원본 환경을 보존한다.
- 대상 배포와 트래픽/DB 전환을 구분한다. 새 대상의 준비만으로 전체 이전 완료를 표시하지 않는다. 원본을 자동 삭제하지 않으며 데이터·세션과 단일 DB 쓰기 원본의 전환은 기존 이전 절차와 연결할 계약을 유지한다.
- 현재 소규모 환경에 맞는 사양 목록을 제공하고, 임의 계정·리전·서브넷·URL·명령은 사용자 입력으로 받지 않는다.

## 구현 단위와 완료 기준

1. 카탈로그·서비스 등록: 배포 선택을 저장하고 기존 서비스는 설정 미지정으로 호환한다. 잘못된 사양과 호스트를 거부한다.
2. 배포 계획·Worker: 승인 해시, 검사한 이미지, 소유 환경, 멱등성, 재시작 후 Jenkins 복구, 대상별 결과와 자동 환경 등록을 연결한다.
3. 실행기: 독립 Jenkins 작업/에이전트, AWS/GCP Terraform 및 온프레미스 YAML 실행 계약을 준비한다. 설정·실제 API 검증·배포 완료를 구분한다.
4. 화면: 등록 시 환경/사양 선택, 최초 배포, 이전 대상 1~2개 선택, 대상별 사양과 진행/실패 상태를 제공한다.
5. 검증: 실제 로컬 PostgreSQL의 API·Worker·실패 복구와 브라우저 흐름, Terraform/실행 계약 검사. 실제 클라우드 Apply·온프레미스 실행은 별도 증거가 있을 때만 완료로 기록한다.

## 구현 상태

2026-11-05 로컬 구현 완료. `platform/` 내 API·Worker·실행기·화면과 플랫폼 CI 검사 목록만 확장했다. 공유 Terraform root, 기존 S3 bucket/state, 팀원 리소스는 변경하지 않았다.

- DB `0009`: 등록 시 선택한 환경·사양을 저장하고 불변 배포 계획을 추가했다. 이전 계획 하나에 서로 다른 대상 실행 두 개를 접수할 수 있다. 기존 등록 API와 소스 검사 해시는 유지한다.
- 계획 검토 해시, 소유 서비스·출발 환경·이미지 digest·대상별 샌드박스 실행/정리 결과를 확인한다. 재요청은 기존 실행을 반환하며 같은 서비스의 다른 작업과 충돌하지 않게 한다.
- 전용 Jenkins Job/Agent 계약을 구현했다. 접수 결과 유실 시 기존 실행을 복구하고 무조건 재접수하지 않는다. 실제 배포 결과가 검증된 경우에만 환경을 자동 등록한다.
- AWS/GCP 새 사설 VM용 독립 Terraform root와 Docker 실행기를 추가했다. 온프레미스는 새 전용 namespace의 FE·BE Deployment/Service, 자원 한도, 앱별 네트워크 정책을 생성한다. 삭제 기능과 같은 서비스·환경 라벨과 UID를 저장한다.
- 등록 화면의 단일 대상·사양, 최초 배포 선택값 복원, 이전 1~2곳 선택, 같은 저장소/커밋의 별도 BE 서비스 빌드 선택, 대상별 진행·실패·사설 주소를 제공한다. 실행 완료 시 환경 목록을 갱신한다.

## 검증 기록

아래 검증은 실제 로컬 PostgreSQL과 브라우저, mock provider/HTTP 경계를 사용했다. 실제 클라우드 배포 성공을 의미하지 않는다.

| 날짜 | 실행 | 결과 |
|---|---|---|
| 2026-11-05 | `cd platform/backend && uv run pytest -q --disable-warnings` | 226 passed, 외부 GitHub live 검사 1개 제외 |
| 2026-11-05 | Node 24에서 `cd platform/web && npm run build && npm run format:check` | 통과 |
| 2026-11-05 | `npx playwright test --config=playwright.fixture.config.ts` | 35 passed |
| 2026-11-05 | 새 AWS/GCP root 각각 `terraform validate && terraform test` | 각각 모의 계획 1개 통과. GCP UUID 이름의 끝 하이픈 문제를 발견해 수정 후 통과 |
| 2026-11-05 | 두 root의 Linux amd64/arm64·macOS arm64 provider lock | 완료 |
| 2026-11-05 | Backend/실행기 `ruff check`, `ruff format --check`, `git diff --check` | 통과 |

새 회귀 검사는 중복 동시 승인, 두 대상 중 한쪽 실패, 원본 보존, 누락 검사 차단, 출발 환경 변경, 승인 해시 불일치, 잘못된 결과 등록 거부, Jenkins 접수 복구 시 중복 POST 방지, 인증된 API 흐름, 온프레미스 자원/삭제 계약, Terraform 기존 자원 삭제·교체 차단을 확인한다.

## 배포 전 남은 연결

현재 운영 플랫폼은 기존 main `5749e67` 배포 상태다. 2026-11-05 사용자에게 구현·검증 결과와 `feat(platform): add deployment targets and multi-target deployment` 메시지를 보고했고, 후속 `Go ahead`로 커밋·PR 진행 승인을 받았다. 이 변경의 게시·원격 CI 결과는 `feat/platform-deployment-targets` 브랜치의 커밋·PR 기록을 따른다. 실제 Apply·운영 배포는 미실행이다.

1. [배포 실행기 연결 문서](../../platform/deploy/workloads/README.md)에 따라 전용 Jenkins Agent/Job과 API 사용자를 준비한다.
2. AWS/GCP의 고객용 subnet·역할/SA·고정 OS 이미지·이미지 저장소, Agent→VM 경로와 온프레미스 kubeconfig·사설 경로를 연결한다. 설정이 없는 대상은 실행 차단 상태다.
3. 작은 단일 앱으로 실제 배포를 확인한 뒤 샘플 FE·BE에 적용한다. 이 구현은 추가 런타임 비밀 값이 없는 앱의 준비 단계다. DB 비밀 값 전달·복제·쓰기 전환·LB/DNS·세션·보안 승인 후 고객 트래픽 전환은 별도 연결이며, 대상 앱 준비만으로 이전 완료라고 표시하지 않는다.
4. PR 검토·병합 후 `0009` migration과 플랫폼 Release를 적용한다. 계획 이력 생성 후 자동 schema downgrade는 거부한다.
