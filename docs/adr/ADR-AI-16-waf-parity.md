# ADR-AI-16: WAF 동등성을 어떻게 판단하고 고칠 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: AWS WAF 규칙을 GCP로 옮길 때 무엇을 동등하다고 볼 것인가?
- 현재 문제와 배경: 데모 안은 AWS에서 GCP로 옮긴 뒤 WAF 유무에 따른 공격 차단을 비교하는 것이다. 두 제품의 규칙은 1:1로 맞지 않는다.
- 범위: WAF만 다룬다. 게이트웨이 선택은 ANF·HAProxy 비교 결과를 따른다.

## Decision Drivers

1. 공격이 실제로 막히는 것을 증거로 삼는다.
2. 시연에서 수정 전후 차이가 분명하다.
3. 잘못된 규칙이 정상 요청을 막지 않는다.

## Considered Options

### Option A: 범주 매핑과 실제 공격 시험 (현재 구현)

- 설명: AWS 관리형 규칙 그룹을 공격 범주로 바꾸고 Cloud Armor 사전 구성 규칙을 제안한다. 동등성 판정은 `PAR-WAF-002`의 공격 결과로 한다. `alert_only`는 차단으로 보지 않는다.
- 장점: 결정적이고 근거를 표로 설명할 수 있다. 같은 범주가 같은 탐지가 아니라는 사실을 시험으로 보완한다. 낮은 민감도로 오탐을 줄인다.
- 단점 및 위험: AWS → GCP만 수정안을 만든다. 크기 제한 등 대응하지 않은 규칙은 안내만 한다. 공격 결과가 없으면 사람 확인이 된다.

### Option B: 규칙 단위 1:1 변환

- 설명: 개별 규칙을 대응 표로 번역한다.
- 장점: 정밀해 보인다.
- 단점 및 위험: 제품 규칙이 1:1이 아니고 관리형 규칙 내부를 다 알 수 없다. 표 유지 비용이 크다.

### Option C: LLM이 규칙 생성

- 설명: LLM이 Cloud Armor 표현식을 만든다.
- 장점: 사용자 정의 규칙까지 대응할 수 있다.
- 단점 및 위험: 잘못된 규칙이 트래픽을 막거나 통과시킬 수 있다. 검증 환경이 전제다.

### Option D: 클라우드 공통 WAF 계층

- 설명: HAProxy와 ModSecurity·Coraza + OWASP CRS처럼 어디서나 같은 규칙을 쓴다.
- 장점: 이전 후에도 규칙이 같다. Beyond Lock-In과 가장 잘 맞는다.
- 단점 및 위험: 운영 책임이 팀에 생기고 HAProxy 데모 범위가 커진다. TLS 복호화 위치도 정해야 한다. 성능과 호환성은 시험하지 않았다.

## Decision

- 선택: Option A 유지. 게이트웨이 비교 결과 HAProxy로 가면 Option D를 다시 검토한다.
- 결정 이유: 지금 시연 안에 가장 빠르게 맞고 실제 공격 결과를 최종 근거로 삼는다.
- 감수한 트레이드오프: 규칙 범위가 완전히 같다고 말할 수 없다. 다른 이전 방향은 사람 처리로 남는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 공격 담당의 시나리오가 범주 밖이거나 반대 방향 이전을 시연하면 다시 본다.

## Follow-up

- 공격 결과 형식과 시나리오를 공격 시험 담당과 맞춘다.
- HAProxy 데모 비교 결과로 Option D 여부를 정한다.
