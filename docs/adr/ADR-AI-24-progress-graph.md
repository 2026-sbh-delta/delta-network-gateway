# ADR-AI-24: 진행 단계 그래프를 어떻게 보여 줄 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다. **아직 구현하지 않았다.**

## Context

- 결정할 질문: 발표에서 AI 판단과 수정의 진행 단계를 어떤 방식으로 그래프로 보여 줄 것인가?
- 현재 문제와 배경: 진행 단계를 그래프로 보여 주는 것이 발표에 중요하다. 그런데 판단 서비스와 점검 에이전트 모두 LangGraph 없이 개발하기로 했고, 구현 방식과 담당은 정하지 않았다. 판단 서비스는 동기 응답 하나만 돌려주므로 처리 중인 내부 단계는 밖에서 보이지 않는다.
- 범위: 시연 진행 화면을 다룬다. 보안·거버넌스 대시보드 전체는 다루지 않는다.

## Decision Drivers

1. 심사위원이 지금 어느 단계이고 왜 분기했는지 바로 이해한다.
2. 실제 실행 결과로 그래프 상태가 바뀐다.
3. 일정 안에 만들고, 판단 서비스의 구조를 그래프 때문에 바꾸지 않는다.

## Considered Options

### Option A: 호출자의 단계 이벤트를 화면이 직접 그림

- 설명: 점검 에이전트나 플랫폼이 단계 시작·종료를 이벤트로 내보내고, 화면이 [시연 워크플로](../architecture.md)의 노드를 칠한다. 판단 노드의 상태는 응답의 `verdict`, `reasons`, `checks`로 정한다.
- 장점: 전 구간(스캔, 판단, 수정, 재시험, 전환)을 한 그래프에 담는다. 판단 서비스를 바꾸지 않는다. 특정 프레임워크에 묶이지 않는다.
- 단점 및 위험: 이벤트 형식과 화면을 새로 만들어야 하고 담당이 필요하다. 판단 서비스 내부 단계는 보이지 않는다.

### Option B: LangGraph로 흐름을 다시 구성

- 설명: 전체나 판단 흐름을 LangGraph로 옮기고 그래프 정의와 단계 스트림을 화면에 쓴다.
- 장점: 정의가 곧 그림이고 그림과 코드가 어긋나지 않는다. 대기 후 재개에도 쓸 수 있다.
- 단점 및 위험: 판단 서비스는 분기가 거의 없어 그릴 내용이 작다. 전체 흐름을 그리려면 에이전트까지 옮겨야 하는데, 담당자가 LangGraph 없이 개발 중이라 재작업이 생긴다.

### Option C: 판단 서비스가 내부 단계를 스트리밍

- 설명: SSE 등으로 규칙 검사, 근거 조회, LLM, 판정 단계를 실시간으로 보낸다.
- 장점: LLM 처리 중에도 화면이 움직인다.
- 단점 및 위험: API가 복잡해지고 ADR-AI-03의 동기 결정을 바꾼다. 단계 대부분이 밀리초 안에 끝나고 LLM 호출만 길어서 볼거리가 작을 수 있다.

### Option D: 발표 자료에 고정 그림과 실행 영상

- 설명: 구조는 슬라이드로 보여 주고 실제 실행은 터미널이나 녹화로 보여 준다.
- 장점: 가장 빠르고 현장 장애에 강하다.
- 단점 및 위험: 실제 상태와 그림이 연결되지 않아 시연 설득력이 약하다.

## Decision

- 선택: Option A 권고. 화면이 늦으면 Option D로 대체한다.
- 결정 이유: 보여 줘야 할 흐름은 대부분 판단 서비스 밖에 있다. 이벤트만 합의하면 어떤 구현이든 붙일 수 있다.
- 감수한 트레이드오프: 그림과 실제 코드가 어긋나지 않도록 사람이 맞춰야 한다. 화면 구현이라는 새 작업이 생긴다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 판단 서비스 안에 분기나 대기 후 재개가 생기면 Option B를 다시 본다. 이때 LangGraph 도입은 점검 에이전트 담당에게 먼저 알린다.

## Follow-up

- 화면 담당을 정한다.
- 이벤트 최소 필드(`run_id`, `step`, `state`, `verdict`, `timestamp`)를 에이전트 담당과 맞춘다.
- 이 응답 필드만으로 판단 노드를 표현하기 어려우면 그때 `meta`에 단계별 시간을 추가한다.
