# ADR-AI-07: 어떤 언어와 웹 스택으로 만들 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 판단 서비스의 언어, 웹 프레임워크, 패키지 도구를 무엇으로 할 것인가?
- 현재 문제와 배경: 본선까지 시간이 짧고 예선 AI 코드는 파이썬이다. HTTP로 호출하므로 다른 팀원의 언어와 맞출 필요는 없다.
- 범위: 판단 서비스 내부 스택만 다룬다.

## Decision Drivers

1. 예선 코드와 경험을 바로 쓴다.
2. 계약을 타입으로 강제하고 JSON Schema로 내보낸다.
3. Claude SDK의 구조화 출력을 쉽게 쓴다.

## Considered Options

### Option A: Python 3.12 + FastAPI + Pydantic + uv·hatchling + pytest (현재 구현)

- 설명: Pydantic 모델이 계약 원본이고 `schema/`는 여기서 생성한다.
- 장점: 예선 코드를 재사용했다. `extra="forbid"`와 `frozen`으로 잘못된 필드와 변경을 막는다. LLM 출력 스키마도 같은 방식으로 만든다.
- 단점 및 위험: 런타임이 크고 컴파일 시점 검사가 약하다. `pyproject.toml`은 하한만 적었으므로 `uv.lock`까지 커밋해야 의존성 버전이 고정된다.

### Option B: Java·Kotlin + Spring Boot

- 설명: 담당자가 경험이 있는 백엔드 스택으로 만든다.
- 장점: 타입이 강하고 운영 도구가 많다.
- 단점 및 위험: 예선 AI 코드를 옮겨야 한다. 일주일 안에 다시 만드는 시간이 판단 품질 작업을 잠식한다.

### Option C: TypeScript + Hono·Fastify + Zod

- 설명: 대시보드와 언어를 맞춘다.
- 장점: 스키마를 프론트와 공유할 수 있다.
- 단점 및 위험: 프론트 스택이 아직 정해지지 않았다. 예선 코드를 옮겨야 한다.

### Option D: Go

- 설명: 단일 바이너리로 만든다.
- 장점: 배포 이미지가 작고 빠르다.
- 단점 및 위험: 스키마 변환과 문자열 처리 코드를 다시 써야 한다. 이 서비스는 대부분 LLM 응답을 기다려 성능 이득이 작다.

## Decision

- 선택: Option A
- 결정 이유: 시간이 가장 큰 제약이다. 호출 계약이 HTTP여서 내부 언어가 다른 팀원에게 영향을 주지 않는다.
- 감수한 트레이드오프: 서비스 언어가 팀 표준과 다를 수 있다. 정적 타입 검사를 아직 CI로 강제하지 않는다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 공유 레포가 단일 언어 빌드만 허용하면 다시 본다.

## Follow-up

- 2026-11-01에 생성된 `uv.lock`을 첫 커밋에 포함하고 이미지 빌드에 사용한다.
- 공유 레포에 넣을 때 테스트 CI를 건다.
