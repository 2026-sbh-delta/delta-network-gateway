# ADR-AI-02: 판단 API를 몇 개의 엔드포인트로 나눌 것인가

> 상태: 제안 · 오너: 김연재 · 작성: 2026-11-01. 확정 전까지 승인된 결정이 아니다.

## Context

- 결정할 질문: 환경 차이, 코드 보안, 피드백 호출을 하나로 묶을 것인가, 나눌 것인가?
- 현재 문제와 배경: 세 호출은 입력이 다르지만 규칙 → 근거 → LLM → 코드 판정 순서와 응답 모양은 같다.
- 범위: 판단 호출만 다룬다. 규칙 후보 승인 API는 이미 별도 경로다.

## Decision Drivers

1. 호출자가 배울 계약이 적다.
2. 잘못된 요청을 스키마만 보고 알 수 있다.
3. 연동 전이라 바꾸는 비용이 낮은 지금 정한다.

## Considered Options

### Option A: 하나의 엔드포인트와 `kind` (현재 구현)

- 설명: `POST /v1/assessments`에 `kind`로 `migration_parity`, `code_security`, `feedback_ingest`를 구분한다.
- 장점: 응답 처리와 `verdict` 분기를 한 벌만 만들면 된다.
- 단점 및 위험: 입력 필드가 선택 값으로 섞여 있다. `kind`별 필수 값을 스키마가 아니라 런타임 검증이 잡는다.

### Option B: `kind`별 엔드포인트

- 설명: `/v1/assessments/parity`처럼 나눈다.
- 장점: OpenAPI 문서만 봐도 호출별 입력이 명확하다.
- 단점 및 위험: 공통 응답 처리는 그대로인데 경로만 세 개로 는다.

### Option C: 하나의 엔드포인트와 구분 유니온

- 설명: 경로는 그대로 두고 Pydantic discriminated union으로 `kind`별 입력 모델을 나눈다.
- 장점: A의 단순함과 B의 스키마 명확성을 함께 얻는다.
- 단점 및 위험: `contract.py`와 스키마 내보내기, 테스트를 고쳐야 한다.

### Option D: gRPC

- 설명: protobuf 계약으로 호출한다.
- 장점: 타입이 강하다.
- 단점 및 위험: curl 시연이 어렵고 팀 전원이 도구를 맞춰야 한다. 해커톤 기간 대비 이득이 작아 깊게 검토하지 않았다.

## Decision

- 선택: Option A 유지. 호출자 형식을 맞출 때 Option C로 바꾸는 것을 허용한다.
- 결정 이유: 세 호출의 처리 순서와 응답이 같아 호출자 코드가 가장 적다. 이 변경은 와이어 형식을 깨지 않는다.
- 감수한 트레이드오프: 스키마만 봐서는 `kind`별 필수 값을 알 수 없고 README 표를 함께 봐야 한다.
- 결정자: 미정 / 결정일: 미정
- 다시 볼 조건: 네 번째 `kind`가 생기거나 팀이 생성 클라이언트를 쓰기로 하면 Option C로 바꾼다.

## Follow-up

- 호출 예시는 `fixtures/`와 README 표를 회의 자료로 쓴다.
